## 문제 정의

기준(프로) 영상과 연습(사용자) 영상을 비교해서 "같은 동작인 지점에서 얼마나
다른가"를 재는 것이 목표다. 이게 성립하려면 세 가지가 필요하다.

1. **관절이 올바르게 탐지되는가** — 배경 간섭, 겹침으로 튀지 않는가
2. **서로 다른 시간대의 같은 동작이 매핑되는가** — 시간축 정렬
3. **두 영상의 좌표를 비교 가능한 형태로 만들 수 있는가** — 촬영 조건(카메라
   거리·위치·기울기) 차이가 동작 차이로 오인되지 않아야 함

3번은 1, 2번이 완벽해도 최종 수치를 무의미하게 만들 수 있어서 별도 축으로 둔다.

## 이번 분석에서 새로 확인한 사실

CLAUDE.md의 "알려진 문제"에 더해, 코드/데이터를 직접 확인해서 밝혀진 것들.

- **`main.py`가 dtaidistance의 1차원 전용 API를 오용 중.** 전체 시퀀스를
  `(프레임수 × 99,)`로 통짜 flatten한 뒤 `dtw.distance()`에 넣어서 프레임 경계가
  사라짐. `window=7`도 "7프레임"이 아니라 "숫자 7개" 범위가 되어 사실상 정렬
  여유가 없음. → D7로 해결
- **0-padding이 "완벽 일치"로 계산됨.** `safe_pad_kp`, `flatten_keypoints`가
  없는 값을 0으로 채우고, 검출 실패 프레임도 통째로 0이 됨. → D2로 해결
- **`extract_pro_sequence.py`가 fps를 읽지도, 반환하지도 않음.** 기준 영상의
  fps가 파이프라인에 아예 들어오지 않아 시간 필터링이 사용자 영상 fps만 사용.
  → D8로 해결
- **`gt.json`으로 mAP를 계산할 수 없음.** annotation에 `bbox`/`area`가 없고
  `images`에 `width`/`height`도 없음. pycocotools `COCOeval(iouType='keypoints')`는
  OKS 계산에 둘 다 요구함. `main.py`에서 `compute_map` 호출이 주석 처리된 이유로
  보임. `evaluate_metrics.py`의 PCK는 대각선을 `1920x1080`으로 하드코딩.
- **`gt.json`이 참조하는 BRACE 이미지 원본이 없음.** `img-000433.jpg` 형식을
  참조하는데 `~/Coding/Dongguk/25-1/개별연구/data/brace/`에 jpg 0개, `video/`도
  비어 있음(`gt_npz/`의 어노테이션만 남음). 추론할 이미지가 없어 현재 어떤
  모델도 이 GT로 평가 불가.
- **모든 pro/user 쌍의 프레임 수가 정확히 동일** (real 393/393,
  candidate1 450/450). 두 영상이 이미 같은 구간으로 잘려 있어 시간 어긋남이
  거의 없을 가능성이 큼. 그렇다면 현재 데이터로는 정렬 개선을 측정할 수 없어
  별도 테스트 케이스가 필요함.
- **동작 비교 품질(L2)에 대한 GT가 아예 없음.** `score`가 나와도 그게 타당한지
  검증할 방법이 현재 없음.
- **`real` 쌍의 프레이밍 차이는 생각보다 작다 (실측).** 두 영상 모두
  1080x1920에 상하 흰 여백이 있고 실제 내용 영역은 각각 1080x892 / 1080x852로
  비슷하다. YOLO-pose로 7개 프레임을 샘플링해 사람 bbox를 재보면
  세로 점유율이 PRO 38.3% / USER 34.0%(폭은 25.7% / 25.9%)로 **스케일 차이가
  약 12%** 수준이다. 즉 좌표 정규화가 필요한 것은 맞지만, 이 쌍에서는 D1(각도
  전환)만으로 점수가 극적으로 변하지는 않을 것으로 보인다. 개선 폭을 과대
  기대하지 말 것.

## 측정 기준

두 층위를 구분한다. 지금까지 "평가"라고 부른 것은 대부분 L1이다.

| 층위 | 재는 것 | GT | 상태 |
|---|---|---|---|
| **L1. 포즈 추정 정확도** | 관절 좌표가 정답에 얼마나 가까운가 (mAP/PCK) | `gt.json` | 코드 있음, **실행 불가** (위 참조) |
| **L2. 동작 비교 품질** | DTW 정렬이 맞게 됐는가 (정렬 오차, 초) | 변형본 dense GT / 앵커 파일 | 변형본 GT **구축 완료**, 앵커는 사용자 대기 |

- L1은 겹침 프레임 **서브셋을 따로** 집계한다. 전체 평균은 안정적인 기본기
  동작에 희석되어 겹침 개선이 보이지 않는다.
- L2는 두 종류의 GT를 쓴다.
  - **자연 촬영 쌍 + 앵커** — 현실성 검증. sparse(10~15점).
  - **합성 변형본** — 정밀 검증. 변형이 결정적이라 모든 프레임의 대응 정답을
    알 수 있어 dense GT가 됨.
- 파이프라인을 변경할 때마다 L2 정렬 오차를 기록해서
  "이 변경으로 오차가 X초 → Y초"를 남긴다. README의 검증 근거가 된다.

**"이 자연 촬영 쌍이 왜 필요했는지"의 직접적인 증거**가 된다.

| 쌍 | 스펙 | 회전 메타데이터 |
|---|---|---|
| natural1 pro | 1920x1080, 30.000fps, 882프레임(29.4초) | 없음 (가로 촬영) |
| natural1 user | 1080x1920(보정 후), 29.986fps, 1101프레임(36.7초) | **90° — D20 버그 발견** |
| natural2 pro | 1280x720, 24.000fps, 440프레임(18.3초) | 없음 |
| natural2 user | 1080x1920(보정 후), 29.985fps, 388프레임(12.9초) | **90° — D20 버그 발견** |

- **natural1/2 user 영상 모두 90° 회전 메타데이터를 갖고 있었고, `cv2.read()`가
  이를 무시**해서 사람이 옆으로 누운 프레임이 그대로 포즈 모델에 들어가고
  있었다. 기존 테스트 영상(`real/`, `candidates/`)은 우연히 raw 버퍼 자체가
  이미 세로로 저장돼 있어 이 문제를 겪지 않았다 → D20으로 해결
- **natural1을 처음 돌렸을 때 크래시.** `compare_sequences`가 채점 가능한
  쌍 0개(`score=None`)를 반환했는데 출력부가 처리 못 함 → 원인은 `max_time_diff`가
  절대 시간차 기준이라 정상적인 고정 오프셋(녹화 시작 시점 차이)까지 전부
  걸러졌기 때문 → D21로 해결. 부수로 크래시 방지 처리도 추가

**D21 수정 검증** (natural1, psi=8초로 진단)

DTW 경로 전체의 시간차 분포: 중앙값 +3.31초, IQR [0.55, 3.68]초 — 대부분의
프레임이 하나의 고정 오프셋 근처에 몰려 있다. 이 중앙값 기준으로 필터링하면:

| 기준 | ±0.6초 내 비율 |
|---|---|
| 절대 시간차 (수정 전) | **0%** |
| 중앙값 대비 상대 시간차 (수정 후) | **57.9%** |

예측한 57.9%와 실제 실행 결과(기본 psi=3.0초)의 채점률 72.9%가 근접 —
(수치가 다른 건 psi 값 자체가 DTW의 동적계획법 해공간을 바꿔서 최적 경로가
달라지기 때문. psi는 후처리 필터가 아니라 탐색 범위 자체를 바꾼다)

**독립적인 두 방법이 서로를 검증함** — natural1의 오프셋을 오디오
크로스코릴레이션(4-B)과 포즈 기반 DTW(이번 실행) 양쪽으로 각각 추정했더니:

| 방법 | natural1 오프셋 |
|---|---|
| 오디오 크로스코릴레이션 | −3.692초 |
| 포즈 DTW (중앙값) | +3.65~3.31초 (부호 규약 반대, 크기는 거의 일치) |

부호를 맞추면 두 방법의 차이가 **0.04초 이내**로 일치한다. 서로 무관한 두
신호(음향 vs 포즈 움직임)가 같은 답을 낸다는 건 둘 다 올바르게 작동한다는
강한 근거다.

**⚠️ natural2에서는 이 일치가 깨진다.**

| 방법 | natural2 오프셋 |
|---|---|
| 오디오 크로스코릴레이션 | +0.882초 (피크 0.390, 신뢰도 5.0 — natural1의 0.596/8.6보다 약함) |
| 포즈 DTW (중앙값) | −3.77초 |

부호를 맞춰도 크기가 4배 이상 차이난다. **원인 미분석.** 후보:
(a) natural2 오디오 추정 자체가 애초에 신뢰도가 낮았음(피크 0.390으로 최소
임계 0.30에 근접), (b) natural2는 fps가 다르고(24 vs 30) pro 해상도가 낮아
(720p) 포즈 DTW 쪽이 흔들렸을 가능성, (c) 채점률도 natural1 72.9% 대비
natural2는 31.0%로 낮아 정렬 자체가 더 어려웠을 가능성. **앵커가 나오면
바로 확인 가능** — 지금은 추측으로 더 파고들지 않는다.

**최종 실행 결과** (기본 설정: window=15, psi-sec=3.0, max-time-diff=0.6)

| 쌍 | 고정 오프셋 | 채점률 | 평균 오차 |
|---|---|---|---|
| natural1 | +3.65초 | 72.9% (760/1043) | 22.64° |
| natural2 | −3.77초 | 31.0% (136/439) | 18.18° |

### Phase 0 결과 — 실제 두 사람 사이에서 angle이 정렬을 개선하는가 (핵심 결과)

앵커가 나온 뒤 가장 먼저 확인한 것. **Phase 2 내내 "증명 못 함"으로 남겨뒀던
바로 그 질문**이다 (합성 변형본은 원본과 같은 사람이라 이걸 증명할 수 없었음).

`tools/eval_alignment.py --mode anchors`로 두 백엔드를 정면 비교:

| 쌍 | feature | 중앙 오차 | ±2프레임 내 | ±5프레임 내 |
|---|---|---|---|---|
| natural1 (n=39) | **angle** | **0.100초** | 41.0% | **71.8%** |
| natural1 (n=39) | coord | 3.668초 | 0.0% | 0.0% |
| natural2 (n=15) | **angle** | **0.100초** | 46.7% | **66.7%** |
| natural2 (n=15) | coord | 2.668초 | 0.0% | 0.0% |

**coord는 사실상 정렬을 전혀 못 했다.** coord의 오차가 두 쌍 모두 그 쌍의
고정 오프셋(아래 참고)과 거의 같은 크기다 — 이는 시간 워핑을 전혀 안 하고
프레임 i를 i에 가깝게 그대로 매칭했다는 뜻이다. 카메라 거리·밝기가 다른
두 사람의 좌표를 직접 비교하니 실제 포즈 유사도 신호가 프레이밍 차이에
완전히 묻힌 것으로 보인다.

**angle은 두 쌍 모두 독립적으로 ±5프레임 내 67~72%를 달성했다.** 서로 다른
안무·다른 촬영 조건의 두 쌍에서 일관된 결과라 우연으로 보기 어렵다.
**Phase 2에서 세운 각도 기반 표현이 실제 두 사람 사이에서도 유효하다는
최초의 실측 증거.**

**다만 완벽하지 않다 — ±2프레임 내는 41~47%에 그친다.** 오차가 큰 앵커를
들여다보면 영상 초반(natural1: pro 프레임 122~299, natural2: pro 프레임
195~272)에 몰려 있다. psi를 키워 재검증했으나 뚜렷한 개선이 없었다
(natural1 ±5f 71.8%→69.2%, natural2는 n이 39→13으로 줄면서 비교 자체가
불안정해짐) — **원인 미규명.** 후보: (a) 초반 동작이 더 모호해 포즈 기반
매칭이 어려움, (b) 사용자의 "동작을 틀리게 실행한 지점" 라벨이 여기 몰려
있을 가능성(안무 구조상 정답과 포즈 유사도 기반 DTW의 판단이 갈리는 지점),
(c) 초반 프레임의 검출 품질. 다음에 시간 나면 라벨과 대조해 확인할 것.

### 오디오 vs 포즈 오프셋 불일치 — 앵커로 해소, 오디오가 틀렸음이 확인됨

이전에 남겨뒀던 미해결 불일치. 앵커에서 직접 계산한 "진짜" 오프셋(앵커
쌍들의 시간차 중앙값)과 비교:

| 쌍 | 오디오 추정 | 포즈 DTW 추정 | **앵커 기준 실제값** |
|---|---|---|---|
| natural1 | −3.692초 | +3.65초 | **+3.647초** |
| natural2 | **+0.882초** | −3.77초 | **−4.756초** |

**natural1은 오디오와 포즈 둘 다 실제값과 거의 일치**(0.005초 이내, 부호는
방향 규약 차이). **natural2는 오디오가 틀렸다** — 실제값(−4.756초)과 부호부터
반대이고 크기도 5배 이상 차이난다. 포즈 DTW(−3.77초)는 부호는 맞지만 여전히
1초가량 벗어나 있다.

**이건 audio_align.py의 신뢰도 임계값이 불충분하다는 뜻이다.** natural2의
피크 상관값은 0.390으로 최소 임계(0.30)를 통과해 "사용 가능"으로 판정됐지만
실제로는 틀렸다. 즉 **`min_peak=0.30`은 명백히 틀린 답(다른 곡 등)을 걸러내는
데는 유효했지만(음성 대조군에서 확인), 임계값을 겨우 넘는 경계 사례의 정확성은
보장하지 못한다.** 필요조건이지 충분조건이 아니다.

**결론**: 오디오 사전 정렬은 검증 없이 단독으로 신뢰하면 안 된다. 현재
계획대로 파이프라인에 연결하지 않은 것이 맞는 판단이었다. 만약 나중에
연결한다면 포즈 기반 DTW와의 교차검증(둘이 크게 다르면 둘 다 버리고
psi 단독에 맡김) 없이는 쓰지 말 것.

나오는데 이는 반올림 오차다 — `evaluate_result/invariance/yolo.json`의 원값 기준.)

- **coord 오차는 변형의 크기 그 자체다.** shift의 경우 적용한 변위를 높이
  단위로 환산하면 `sqrt((0.12 x 1080/1920)^2 + 0.08^2) = 0.1047`로 측정값과
  정확히 일치한다. 즉 좌표 feature는 동작 차이가 아니라 프레이밍 차이를 재고 있다.
- **angle 오차는 변형 종류와 무관하게 3.2~3.5도로 일정하다.** coord 영향이
  5.7배 차이나는(0.0184 vs 0.1047) 세 변형에서 angle이 거의 같다는 것은,
  남은 오차가 변형 때문이 아니라 포즈 추정 흔들림임을 뜻한다.
- **D5(몸통 축 자가 보정)가 작동한다.** 카메라를 8도 돌렸는데 `torso_tilt`
  오차는 1.0도에 그친다. 보정이 없었다면 8도가 그대로 나와야 한다.

**feature별 노이즈 바닥** (중앙값, 도)

| feature | 대조군(노이즈 바닥) | roll 8도 | 실제 두 댄서 |
|---|---|---|---|
| torso_tilt | 0.3 | 1.0 | 5.0 |
| thigh / shin / knee_bend | 0.5~0.6 | 2.4~3.2 | 8.6~11.8 |
| upper_arm | 0.4 | 2.2~2.3 | 11.5~14.2 |
| neck | 0.9 | 2.8 | 16.0 |
| **forearm** | 0.5~0.6 | 2.9~3.0 | **29.9~30.1** |
| **elbow_bend** | 0.7~0.8 | 3.8~4.3 | **27.1~30.3** |

**⚠️ 가설이 반증되었다.** 전완·팔꿈치 오차가 유독 큰 것을 보고 처음에는
"손목 키포인트가 부정확하고 짧은 분절이라 각도로 증폭된다"고 추정했으나,
측정 결과 전완의 노이즈 바닥(0.5~0.6도)과 roll 반응(2.9~3.0도)은 허벅지
(0.6도 / 2.4도)와 사실상 같다. 즉 전완 feature 자체는 다른 것들만큼 안정적이다.
따라서 실제 쌍에서의 30도는 **feature 결함이 아니라 두 댄서의 실제 팔 동작
차이**이거나 **그 구간의 정렬 오류**다. 둘을 구분하려면 앵커가 필요하다.

**정렬 정확도 — angle vs coord** (변형본 dense GT, window=15)

| 변형 | angle ±2f내 | coord ±2f내 |
|---|---|---|
| offset60 | 96.4% | 97.6% |
| speed 0.90 | 100.0% | 100.0% |
| local 0.50 | 100.0% | 100.0% |

**이 표로 angle의 우위를 주장할 수 없다.** 변형본은 원본과 같은 영상이라
프레이밍 차이가 0이고, 그 조건에서는 coord가 불리할 이유가 없다(오히려 약간
덜 흔들린다). angle의 이점은 위의 불변성 표에서만 드러난다. 프레이밍이 다른
두 댄서 사이에서 angle이 정렬을 개선하는지는 **아직 측정되지 않았고**,
사용자의 자연 촬영 쌍 + 앵커로만 확인할 수 있다.

**실제 쌍 실행 결과** (`real`, yolo, angle)
- 점수 45.7 (잠정) | 평균 오차 24.45도, 중앙 21.52도, p90 42.21도
- 몸통 기준각 자가 보정: 사용자 +2.2도, 기준 +0.9도 (실제로 롤 차이가 있었음)
- 정면성 중앙값: 사용자 0.641, 기준 0.646 (두 영상의 촬영 각도가 비슷함)
- 리포트가 해석 가능해짐 — 예전 `joint 8, distance 0.34` → 지금
  `r_elbow_bend 128도`

**Phase 3에 대한 예측 (검증 필요)** — 같은 쌍을 yolo와 mediapipe로 각각 돌리면
각도 오차가 평균 24.45도 / 24.80도, 중앙 21.52도 / 21.35도로 거의 같다.
구조가 꽤 다른 두 모델이 이렇게 근접한다는 것은, 측정되는 값의 대부분이 모델
차이가 아니라 **두 댄서의 실제 동작 차이**임을 시사한다. 그렇다면 Phase 3의
모델 교체로 이 수치가 크게 움직이지 않을 수 있다. 모델 교체의 효과는 전체
평균이 아니라 **겹침 구간 서브셋**에서 봐야 한다는 근거이기도 하다.

## Phase 3 — 모델 비교

### 3-A. GT 없이 가능한 부분 ✅ 완료

L1 GT가 없으면 "어느 모델이 정확한가"의 **순위**는 못 매긴다. 하지만 라벨 없이
잴 수 있는 품질의 필요조건들이 있어서 먼저 처리한다. `tools/eval_pose_quality.py`

- [x] MediaPipe 모델 크기 선택 가능하게 수정 — 모듈 로드 시점에 `complexity=0`
      싱글톤으로 고정돼 있어서 Lite/Full/Heavy를 바꿀 수 없었다
- [x] ultralytics 대형 체크포인트 확보 (yolov8x-pose 139MB, yolo11x-pose 118MB).
      새 의존성 없이 되는 무료 업그레이드
- [x] `transformers` / `onnxruntime` 설치 — **dry-run으로 고정 버전이 안 바뀌는
      것을 먼저 확인**했고, 설치 후 numpy 1.26.4 / mediapipe 0.10.21 /
      ultralytics 8.3.155 / dtaidistance 2.3.13 전부 무사함을 재확인
- [x] `tools/eval_pose_quality.py` — 라벨 없는 품질 지표
- [x] ViTPose 백엔드 (`src/pose_vitpose.py`) — HuggingFace transformers 5.16.1,
      `usyd-community/vitpose-base-simple`. 단일 프레임 검증 통과
      (score 중앙 0.855, 좌표계 정상)
- [x] RTMPose 백엔드 (`src/pose_rtmpose.py`) — **mmcv 없이** rtmlib + onnxruntime.
      `rtmpose-l_simcc-body7 384x288` ONNX 자동 다운로드(99MB).
      단일 프레임 검증 통과 (score 중앙 0.727)
- [x] 전체 모델 품질/비용 비교표 (아래 결과)

**top-down인데 hybrid와 다른 이유** — ViTPose/RTMPose도 사람 bbox를 먼저 받는
top-down이라 폐기된 hybrid와 구조가 같아 보인다. 하지만 hybrid는 프레임을
**직접 잘라서**(`frame[y1:y2, x1:x2]`) 포즈 모델에 넘겼고 그 과정에서 종횡비가
깨지고 경계에서 신체가 잘렸다. 이 둘은 라이브러리가 종횡비를 지키며 패딩·아핀
변환으로 정규화하고 출력을 원본 좌표계로 되돌린다. 즉 **top-down이 문제였던 게
아니라 hybrid의 crop 구현이 문제였다.**

**라벨 없이 재는 것들**
1. **뼈 길이 안정성** — 사람 몸은 강체다. 프레임 간 뼈 길이가 급변하면 동작이
   아니라 추정 오류다. 겹침 구간에서 모델이 가려진 관절을 지어내면 여기서
   잡힌다. 즉 **라벨 없는 겹침 오류 탐지기** (알려진 문제 2를 정면으로 겨냥).
   투영 단축은 부드럽게 변하므로 프레임 간 급변만 보면 단축과 오류가 구분된다.
2. **시간적 흔들림** — 같은 영상이면 실제 움직임이 동일하므로 차이는 모델 흔들림.
3. **모델 간 불일치** — 정답을 몰라도 "여기가 어렵다"는 알 수 있다.
   → **L1 GT 라벨링 대상 프레임을 무작위가 아니라 여기서 고른다.**
      겹침 서브셋을 원리적으로 구성하면서 라벨링 효율도 올라간다.
4. **비용** — fps / latency / memory.

**⚠️ 모델 간 "유효율"은 비교하면 안 된다.** 신뢰도 캘리브레이션이 모델마다
다르다. 실측에서 yolov8x가 yolov8n보다 유효율이 낮게 나왔는데(91.8% vs 93.3%)
이는 큰 모델이 나쁜 게 아니라 과신하지 않는다는 뜻일 수 있다. 그래서 품질
지표는 낮은 임계값(0.1)으로 계산한다 — 걸러낸 뒤가 아니라 걸러내기 전의
기하학적 일관성을 봐야 모델끼리 공정하다.

**⚠️ `memory_MB` 열은 신뢰하지 말 것.** `tracemalloc`은 파이썬 수준 할당만
추적하므로 torch/ONNX가 C++ 쪽에서 잡는 메모리가 빠진다. 실제로 yolov8n이
78MB, yolov8x가 14MB로 역전되어 나온다. 비교하려면 RSS를 따로 재야 한다.

#### 결과 — 라벨 없는 모델 품질

아래 세 표는 **서로 다른 시점의 별도 실행**이다. 품질 지표(뼈 불안정/흔들림)는
실행 간 재현되지만 fps/지연은 백그라운드 부하에 따라 흔들리므로, **속도 비교는
같은 표 안에서만 하고 표를 가로질러 비교하지 말 것.** 최종 판단은 세 번째
표(5모델)를 기준으로 한다.

**(1) 초기 6모델 — YOLO/MediaPipe 계열 크기별** (`real/user_dancer.mp4` 393프레임, M2)

| 모델 | 뼈 불안정 ↓ | 흔들림 ↓ | fps | 지연 ms |
|---|---|---|---|---|
| yolov8n-pose (현재 기본) | 0.0143 | 0.0381 | 25.3 | 39.5 |
| yolov8x-pose | 0.0139 | 0.0383 | 6.8 | 146.2 |
| **yolo11x-pose** | **0.0127** | 0.0363 | 6.3 | 159.6 |
| mediapipe Lite (0) | 0.0211 | 0.0383 | 38.5 | 26.0 |
| mediapipe Full (1) | 0.0186 | 0.0364 | 33.4 | 29.9 |
| mediapipe Heavy (2) | 0.0171 | 0.0357 | **2.4** | 408.5 |

읽는 법:
- **yolo11x가 뼈 안정성 1위** (0.0127). 다만 yolov8n 대비 11% 개선에 비용은
  4배다. yolov8n→yolov8x는 3% 개선에 3.7배 비용으로 **사실상 무의미**하다.
  "모델을 키우면 좋아진다"는 기대만큼 오지 않는다.
- **MediaPipe는 모든 크기에서 YOLO 계열보다 뼈 안정성이 나쁘다**(0.0171~0.0211).
- **MediaPipe Heavy는 채택 근거가 없다.** yolo11x보다 느리면서(2.4 vs 6.3fps)
  뼈 안정성도 나쁘다(0.0171 vs 0.0127). Lite/Full은 속도 이점이라도 있지만
  Heavy는 두 축 모두 진다.

**(3) 최종 5모델 — 판단 기준** (`real/user_dancer.mp4` 393프레임)

| 모델 | 뼈 불안정 ↓ | 흔들림 ↓ | fps | 지연 ms | 실행 장치 |
|---|---|---|---|---|---|
| yolov8n-pose (현재 기본) | 0.0143 | 0.0381 | 26.0 | 38.4 | MPS |
| **yolo11x-pose** | **0.0127** | **0.0363** | 5.7 | 176.7 | MPS |
| mediapipe Full | 0.0189 | 0.0372 | 29.1 | 34.4 | CPU/GPU |
| ViTPose-base-simple | 0.0136 | 0.0367 | 6.0 | 167.8 | MPS |
| RTMPose-l (384x288) | 0.0150 | 0.0389 | 3.6 | 274.9 | **CPU** |

**yolo11x-pose가 두 품질 지표 모두 1위다.** "SOTA"로 넣은 ViTPose와 RTMPose가
둘 다 이기지 못했다. 특히 RTMPose-l은 뼈 안정성이 0.0150으로 **yolov8n(0.0143)
보다도 나쁘다.**

⚠️ **해석 시 반드시 붙여야 할 단서 4개**
1. **RTMPose만 CPU(onnxruntime)에서 돌았다.** 다른 모델은 MPS다. 따라서
   fps/지연 비교는 RTMPose에 불리하다. 품질 지표는 장치와 무관하므로 유효하다.
2. **모델 크기가 맞춰지지 않았다.** ViTPose는 base(large 아님), RTMPose는
   l(x 아님)이다. "ViTPose/RTMPose가 나쁘다"로 일반화할 수 없다.
3. **이 지표들은 정확도의 대리 지표지 정확도가 아니다.** 뼈 안정성이 높아도
   일관되게 틀린 위치를 찍을 수 있다. 순위 확정은 L1 GT가 필요하다.
4. **테스트 영상이 쉽다.** 5개 모델 모두 검출 실패 0프레임, 유효율 92~100%다.
   정작 중요한 겹침 구간이 스트레스되지 않았으므로, **겹침이 많은 영상에서는
   순위가 바뀔 수 있다.** 이 비교는 "쉬운 영상에서의 기본 안정성" 측정이다.

**실무적 결론**: yolo11x가 yolov8n 대비 뼈 안정성 11% 개선인데 비용은 4.6배다.
겹침 서브셋에서 차이가 훨씬 크게 나지 않는 한, 이 개선폭만으로 4.6배를 지불할
근거는 약하다. 단, 아래 서브샘플링과 조합하면 얘기가 달라진다.

**(2) ViTPose 추가 측정**

| 모델 | 뼈 불안정 ↓ | 흔들림 ↓ | fps | 지연 ms |
|---|---|---|---|---|
| yolov8n-pose | 0.0143 | 0.0381 | 27.4 | 36.5 |
| **yolo11x-pose** | **0.0127** | 0.0363 | 5.2 | 191.9 |
| mediapipe Full | 0.0189 | 0.0372 | 23.2 | 43.0 |
| ViTPose-base-simple | 0.0136 | 0.0367 | 4.7 | 213.0 |

**ViTPose가 yolo11x를 못 이겼다.** 뼈 안정성 0.0136 vs 0.0127로 오히려 뒤지고
속도도 느리다(4.7 vs 5.2fps). "정확도 천장 참조점"으로 넣었는데, 적어도 이
지표에서는 천장이 yolo11x보다 위에 있지 않다. base 크기라서일 수 있으므로
large 계열을 확인하기 전에는 "ViTPose가 나쁘다"로 일반화하지 말 것.

#### 모델 간 불일치 (중앙값, 몸통길이 정규화)

| 쌍 | 불일치 |
|---|---|
| yolov8x vs yolo11x (같은 계열) | 0.0326 |
| mediapipe:1 vs mediapipe:2 (같은 계열) | 0.0342 |
| **yolo11x vs ViTPose (계열은 다르지만 둘 다 상위)** | **0.0388** |
| yolov8n vs yolov8x | 0.0630 |
| YOLO 계열 vs MediaPipe 계열 | 0.0565~0.0733 |

**뼈 안정성 상위 두 모델(yolo11x, ViTPose)이 서로 가장 근접한다**(0.0388).
계열이 다른데도 계열 내부 수준으로 일치한다는 것은, 둘 다 같은 지점으로
수렴하고 있다는 뜻으로 읽을 수 있다 — 라벨 없이 얻을 수 있는 간접적인
정확도 신호다. 다만 이는 추론이지 증명이 아니며, L1 GT로 확인해야 한다.

**계열 내부(0.033)보다 계열 간(0.057~0.073)이 2배 크다.** 계열 간 차이에는
"어려운 프레임"뿐 아니라 관절 정의의 체계적 차이(COCO17 vs BlazePose의
어깨·엉덩이 위치 규약)가 섞여 있다는 뜻이다. 따라서 **L1 라벨링 대상 프레임을
고를 때는 같은 계열 두 모델의 불일치(yolov8x vs yolo11x)를 쓰는 편이 깨끗하다** —
체계적 오프셋이 상쇄되어 진짜 어려운 프레임만 남는다.

### 3-B. 프레임 서브샘플링 트레이드오프 (완료)

`tools/eval_subsample.py`. 변형본 dense GT로 측정하므로 앵커가 필요 없다.

| 배수 | 유효 fps | 연산량 | 중앙 오차 | 평균 오차 | 해상도 하한 | ±5프레임 내 |
|---|---|---|---|---|---|---|
| x1 | 30.0 | 100% | 0.000초 | 0.003초 | 0.017초 | 100% |
| x2 | 15.0 | 50% | 0.000초 | 0.007초 | 0.033초 | 100% |
| x3 | 10.0 | 33% | 0.033초 | 0.030초 | 0.050초 | 100% |
| x4 | 7.5 | 25% | 0.000초 | 0.033초 | 0.067초 | 100% |
| x6 | 5.0 | 17% | 0.067초 | 0.049초 | 0.100초 | 100% |

offset 변형에서는 x6까지도 중앙 오차가 0.000초로 사실상 평평하다.

**오차가 해상도 하한(k/2 프레임)을 따라간다.** 즉 성능 저하의 대부분은
알고리즘이 무너져서가 아니라 시간 해상도 자체의 한계다. x6(5fps)에서도
±5프레임 내 100%를 유지한다.

**이게 모델 선택을 바꾼다.** 서브샘플링으로 아낀 연산을 더 좋은 모델에 쓸 수 있다:

| 구성 | 원본 프레임당 실효 비용 | 뼈 불안정 |
|---|---|---|
| yolov8n @ 30fps | 38.4ms | 0.0143 |
| **yolo11x @ 10fps (x3)** | **58.9ms** | **0.0127** |
| yolo11x @ 30fps | 176.7ms | 0.0127 |

yolo11x를 10fps로 돌리면 yolov8n 30fps의 1.5배 비용으로 더 나은 품질을 얻는다.
"무거운 모델은 비싸서 못 쓴다"는 전제가 서브샘플링과 결합하면 성립하지 않는다.

#### 서브샘플링이 **채점**에 미치는 영향 (`tools/eval_subsample_scoring.py`)

위 표는 정렬(L2)만 잰 것이라 채점을 따로 측정했다. 정렬이 멀쩡해도 프레임을
띄엄띄엄 보면 빠른 동작의 순간 오차를 놓칠 수 있기 때문이다.
앵커가 필요 없다 — k=1(전체 프레임) 자체가 기준이다.

`real` 쌍, yolo, angle:

| 배수 | 점수 | 평균 | p90 | 최대 | 채점쌍 |
|---|---|---|---|---|---|
| x1 (30fps) | 46.4 | 24.11도 | 42.18 | 104.62 | 455 |
| x2 | 48.4 | 23.20 | 37.83 | 86.60 | 212 |
| x3 | 46.6 | 24.02 | 37.87 | 90.01 | 134 |
| x4 | 49.6 | 22.69 | 35.99 | 62.84 | 104 |
| x6 (5fps) | **54.0** | 20.72 | 32.69 | 47.27 | 47 |

**프레임을 덜 봤다는 이유만으로 점수가 올라간다**(46.4 → 54.0).

**⚠️ 다만 채점쌍 수도 455 → 47로 줄어든다.** 표본이 작아지면 최대값은 그것만으로도
낮아지므로, 하락분이 정보 손실인지 통계적 효과인지 구분해야 한다.
→ k=1의 오차 분포에서 **같은 개수만 무작위 추출(1000회)** 하는 대조군으로 분리:

| 배수 | n | p90 실제 vs 대조 | 최대 실제 vs 대조 |
|---|---|---|---|
| x2 | 212 | 37.83 vs 41.99±1.49 (**−2.8σ**) | 86.60 vs 93.06±13.77 (−0.5σ) |
| x3 | 134 | 37.87 vs 42.07±2.15 (**−2.0σ**) | 90.01 vs 85.54±16.30 (+0.3σ) |
| x4 | 104 | 35.99 vs 41.93±2.55 (**−2.3σ**) | 62.84 vs 80.28±16.85 (−1.0σ) |
| x6 | 47 | 32.69 vs 41.49±4.55 (**−1.9σ**) | 47.27 vs 69.03±17.74 (−1.2σ) |

**결론 (경보를 절반 정정한다)**
- **"최대 오차가 최대 54.8% 사라진다"는 처음 관찰은 과했다.** 대조군 편차가
  ±14~18로 커서 실제값과 구분되지 않는다. 최대값은 표본 크기에 지나치게 민감해
  이 목적의 지표로 부적절하다.
- **p90은 모든 배수에서 일관되게 약 2σ 아래**다. 이건 표본 축소로 설명되지 않는
  **실제 정보 손실**이다. 크기는 p90 기준 10~22% 과소평가.
- 즉 서브샘플링은 채점을 **낙관적으로 편향**시킨다. 파국은 아니지만 실재한다.

**설계 권고**: 정렬과 채점의 요구가 다르므로 분리한다.
- **정렬**은 서브샘플링에 강건(x6까지 ±5프레임 100%) → 띄엄띄엄 처리해도 된다
- **채점**은 정보 손실이 있으므로 전체 프레임 권장
- 최선은 **서브샘플로 정렬 경로를 구하고, 그 경로를 보간해 전체 프레임에서 채점**하는
  것이다. 무거운 포즈 추정은 정렬용으로만 띄엄띄엄 돌리고 채점은 촘촘하게.
  (미구현 — 다음 작업 후보)

### 3-C. Subsequence 정렬 — psi 끝점 완화 (완료)

**문제**: 일반 DTW는 경로가 (0,0)에서 시작해 (n-1, m-1)에서 끝나도록 강제한다.
두 영상이 처음부터 끝까지 대응한다는 가정인데, 실서비스에서는 사용자가 안무의
일부만 추거나 시작 전/끝난 후 여백이 들어가는 게 훨씬 흔하다. 그러면 대응
없는 구간까지 억지로 이어붙이며 정렬 전체가 망가진다.

**해결**: dtaidistance의 psi 완화. 양 끝에서 최대 psi프레임까지 대응 없이
건너뛸 수 있게 한다. `align(..., psi=N)`.
주의 — psi가 짧은 쪽 시퀀스 길이를 넘으면 dtaidistance가 IndexError로 죽는다.
`align()`에서 잘라낸다.

**검증**: `trim` 변형본 추가 (원본의 25%~70% 구간만 = 앞 98프레임, 뒤 118프레임이
기준 영상에 대응 없음).

| psi | 평균 오차 | 최대 오차 | ±5프레임 내 |
|---|---|---|---|
| 없음 (끝점 강제) | 0.446초 | 3.733초 | 83.1% |
| 30 | 0.323초 | 2.333초 | 83.5% |
| 60 | 0.208초 | 1.433초 | 83.5% |
| **100** | **0.002초** | 0.317초 | **99.4%** |
| 130 | 0.000초 | 0.017초 | 100% |

**psi가 잘려나간 앞부분(98프레임) 이상이 되는 지점에서 정확히 정렬이 붙는다.**
psi < 98에서는 부족한 만큼 오차가 남는다.

**psi를 크게 걸어도 손해가 없다** — 전체가 정상 대응하는 변형본들에서 확인:

| 변형 | psi 없음 (평균) | psi=100 (평균) | psi 없음 ±5f | psi=100 ±5f |
|---|---|---|---|---|
| trim | 0.446초 | **0.002초** | 83.1% | **99.4%** |
| offset60 | 0.074초 | **0.001초** | 96.4% | **100%** |
| speed 0.90 | 0.002초 | 0.002초 | 100% | 100% |
| local 0.50 | 0.003초 | 0.003초 | 100% | 100% |

손해는 없고 trim/offset 두 곳에서 이득이므로 **기본으로 켠다** (D19).
인자는 초 단위(`--psi-sec`, 기본 3.0)로 받아 fps로 환산한다 — 영상마다 fps가
다르므로 프레임 수로 고정하면 안 된다.

⚠️ 관측 범위의 한계: 변형본 4종·영상 1개에서만 확인했다. psi가 지나치게 크면
실제 대응해야 할 구간을 건너뛸 수 있다는 이론적 위험은 남아 있고, 여기서는
관측되지 않았을 뿐이다. 3.0초는 그 위험과 커버리지 사이의 잠정적 절충이다.

### 4-B. 오디오 사전 정렬

춤은 음악에 맞춰 추므로 같은 곡이면 오디오만으로 전역 오프셋을 확정할 수 있다.
그러면 DTW는 미세 타이밍만 다루면 되므로 탐색 공간이 줄고 정렬 실패도 준다.

**원파형이 아니라 온셋 포락선을 쓴다** — 따로 촬영하면 마이크·거리·잔향이 달라
파형은 잘 안 맞지만, "소리가 커지는 순간"은 녹음 조건과 무관하게 같은 시점에 있다.

**정답을 아는 케이스 검증** (오디오를 정확히 잘라낸 뒤 복원)

| 정답 오프셋 | 추정값 | 오차 |
|---|---|---|
| 2.000초 | 1.997초 | 3ms |
| 0.700초 | 0.697초 | 3ms |

3ms는 포락선 해상도(86fps → 11.6ms) 안쪽이다.

**⚠️ 음성 대조군에서 판별기가 처음엔 실패했다.** 서로 다른 영상끼리도 신뢰도
9~10이 나와 임계 3.0을 통과했다. 원인을 파보니:

| 쌍 | 피크값 | 피크 위치 | lag 0 상관 |
|---|---|---|---|
| real pro↔user | **1.0000** | 0.00초 | 1.0000 |
| candidate1 | 0.5289 | **+10.25초** | 0.0440 |
| candidate2 | 0.5073 | **−12.21초** | −0.0010 |
| candidate3 | 0.4827 | **−10.88초** | −0.0051 |

허위 피크가 전부 **끝단 lag**(13초 영상에서 ±10~12초 = 겹침이 최소인 지점)에서
나왔다. 표본이 적으면 정규화 상관이 우연히 높아지기 때문이다. z-score만으로는
이걸 구분할 수 없었다.

**수정** — 판별 기준 3개를 함께 적용:
1. 겹침 50% 이상만 후보로
2. 오프셋 범위를 짧은 쪽 길이의 30% 이내로 제한
3. **피크 상관값 자체**에 하한(0.30). z-score는 보조 기준으로만

**수정 후**

| 쌍 | 결과 |
|---|---|
| 정답 2.0초 / 0.7초 | 사용 가능 (피크 0.82) ✅ |
| real pro↔user | 사용 가능, 오프셋 +0.000초 (피크 1.000) |
| candidate 1/2/3 | **사용 불가** — 피크 0.16~0.28 < 0.30 ✅ |

**⚠️ 이 검증의 큰 한계** — `real` 쌍의 피크 상관이 **정확히 1.0000**이다. 즉 두
영상이 **동일한 오디오 트랙을 공유**한다(같은 소스에서 잘렸거나 더빙). 따라서
"따로 촬영해 음향 환경이 다른 두 영상"이라는 **실제 사용 조건은 이 데이터로
검증되지 않았다.** 온셋 포락선을 쓴 이유가 바로 그 조건 때문인데, 정작 그 조건을
테스트하지 못했다. 사용자의 자연 촬영 쌍이 확보되면 가장 먼저 확인할 것.

**아직 파이프라인에 연결하지 않았다.** 도구로만 존재한다. `real` 쌍의 오프셋이
0.000초라 붙여도 효과를 볼 수 없고, 효과를 확인할 데이터가 생긴 뒤에 붙이는 게
맞다고 판단했다.

### 가설 검증

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| (c) 초반 프레임의 검출 품질이 낮다 | 앵커 주변 ±5프레임의 관절 유효율 vs 정렬 오차 상관 | ❌ **배제.** 상관계수가 두 쌍에서 부호조차 반대(−0.326 / +0.188), 품질 차이도 0.908 vs 0.953으로 미미 |
| (b) 사용자가 동작을 틀리게 실행한 지점이라 DTW가 헤맨다 | **정답 지점 vs DTW가 고른 지점의 포즈 오차 비교** | ✅ **지지됨** (아래) |
| (a) 초반 동작이 모호하다 | — | 미검증 (b와 분리 곤란) |

### 핵심 발견 1 — DTW는 실패한 게 아니라 목적함수에 충실했다

앵커마다 "정답 지점의 포즈 오차"와 "DTW가 실제로 고른 지점의 포즈 오차"를 비교:

| 쌍 | 정답 지점 | DTW 선택 지점 | DTW가 더 비슷한 곳을 고른 비율 |
|---|---|---|---|
| natural1 (39개) | 27.6° | 24.5° | **67%** |
| natural2 (15개) | 29.9° | 26.6° | **60%** |
| natural1, 정렬오차>0.2초인 11개 | 35.4° | 31.7° | 55% |
| natural2, 정렬오차>0.2초인 5개 | 35.2° | 29.3° | **80%** |

**DTW는 정답보다 포즈가 더 비슷한 곳을 골랐다.** 즉 알고리즘 버그가 아니라
**"포즈 유사도 ≠ 안무 구조"라는 원리적 한계**다. 그리고 정렬 오차가 큰 앵커는
정답 지점의 포즈 오차 자체가 높다(35°, 전체 평균 27.6° 대비) — 사용자가 그
지점에서 실제로 동작을 크게 다르게 했다는 뜻이다.

**⚠️ 제품 관점의 함의**: 사용자가 동작을 틀리게 할수록 정렬이 어긋나고, 정렬이
어긋나면 채점도 틀린다. 즉 **잘 추는 사람에게는 정확하고 못 추는 사람에게는
부정확해지는 되먹임**이 있다. 그런데 못 추는 사람이야말로 이 서비스의 주
사용자다. 이건 근본적 한계로 문서화해야 한다.

### 핵심 발견 2 — 밴드 제약이 무력화돼 있었다 (버그)

`align()`은 경로 존재를 보장하려고 `window = max(요청값, |길이차| + 1)`로 넓힌다.
그런데 두 영상 길이가 크게 다르면 이 가드가 밴드를 통째로 무력화한다.

| 쌍 | 길이차 | 요청 window=15 | 실제 적용 |
|---|---|---|---|
| natural1 | 219프레임 | 15 | **220프레임 (7.3초)** |
| natural2 | 52프레임 | 15 | 53프레임 |

앞서 "window를 15~150으로 스윕해도 결과가 동일하다"고 기록한 것의 진짜 이유가
이것이다 — **애초에 값이 무시되고 있었다.** 제약이 없으니 DTW가 발견 1처럼
멀리 도망갈 자유를 갖게 된다.

### 개선 시도 — 2단계 정렬 (미완성)

길이차와 국소 워핑을 분리해 처리하는 구조를 시도했다 (`align_two_pass`):
1단계에서 전역 추세(오프셋+기울기)를 추정해 대각선을 맞추고, 2단계에서 좁은
밴드로 국소 워핑만 허용한다.

**시도 1 — 오프셋만 median으로 제거 (기울기는 fps비 고정)**

| 쌍 | 기존 ±5f | 2단계 w=5 |
|---|---|---|
| natural1 | 71.8% | **94.9%** |
| natural2 | 66.7% | **86.7%** |

큰 개선. 그러나 **합성 변형본에서 붕괴**했다 — speed0.90이 100%→32.9%,
local0.50이 100%→6.6%. 원인: fps 비율만으로는 전역 배속 차이를 제거하지 못한다
(speed 변형은 fps가 같고 프레임 수만 다르다).

**시도 2 — 기울기를 최소제곱(polyfit)으로 추정**

합성은 회복(speed 100%)됐으나 **자연 촬영이 붕괴**했다 (natural1 w=5:
94.9% → 15.4%). 원인: 1단계 경로에는 DTW가 멀리 도망간 구간이 섞여 있고,
최소제곱이 그 이상치에 끌려간다.

**시도 3 — Theil-Sen(점쌍 기울기 중앙값)으로 강건화**

| | 합성 local0.50 | 합성 trim | natural1 ±5f | natural2 ±5f |
|---|---|---|---|---|
| 기존 | 100% | 98.9% | 71.8% | 61.5% |
| 2단계 w=40 | 100% | 59.9% | 74.4% | 40.0% |
| 2단계 w=80 | 100% | 98.9% | 69.2% | 69.2% |

합성은 w=80에서 기존 수준을 회복하지만, **자연 촬영에서의 개선이 미미**하다
(시도 1의 94.9%가 재현되지 않음).

**왜 재현되지 않는가 — 기울기 추정 자체가 부정확했다**

| 쌍 | DTW 1단계 추정 | 앵커 기준 정답 |
|---|---|---|
| natural1 | slope 1.0991, offset 58.8 | **slope 1.0000, offset 109.0** |
| natural2 | slope 0.8716, offset −12.0 | **slope 1.2361, offset −138.9** |

**1단계 DTW의 경로가 이미 부정확하기 때문에 거기서 뽑은 추세도 틀린다.**
natural1의 진짜 기울기는 1.0(같은 속도)인데 1.0991로 추정했고, natural2는
방향조차 반대다(0.87 vs 1.24). 시도 1이 잘 됐던 건 slope를 fps비(≈1.0)로
**고정**해서 우연히 정답에 가까웠기 때문이지, 추정이 잘돼서가 아니었다.

→ **순환 문제**: 좋은 정렬을 얻으려면 좋은 추세 추정이 필요한데, 추세 추정은
정렬 결과에 의존한다. 이걸 끊으려면 정렬과 무관한 독립 신호가 필요하다.

### 시도 4 — 비율(정규화 위치) 기반 밴드

사용자 제안. 밴드를 절대 프레임차 `|i − j|`가 아니라 **정규화 위치차
`|i/n_pro − j/n_user|`** 로 정의한다. 두 영상 길이가 다르면 정상 경로도 `|i−j|`가
커지므로 절대 밴드가 무력화될 수밖에 없는데(발견 2), 정규화하면 **길이 비율이
자동으로 처리되고 추정이 필요 없다.** 시도 2·3이 기울기를 추정하려다 순환 문제에
빠진 것과 대조적이다 — 길이는 이미 아는 값이다.

구현은 user를 pro 길이에 비례 대응시켜 재샘플한 뒤 밴드를 적용하는 것으로 등가.

**합성 변형본 (±2프레임 내)**

| 변형 | 기존 | r=.02 | r=.05 | r=.10 | r=.20 | r=.30 |
|---|---|---|---|---|---|---|
| speed 0.90 | 100% | **100%** | 100% | 100% | 100% | 100% |
| speed 1.10 | 100% | **100%** | 100% | 100% | 100% | 100% |
| local 0.50 | 100% | 32.4% | 73.2% | **100%** | 100% | 100% |
| offset60 | 100% | 15.9% | 35.4% | 67.3% | **100%** | 100% |
| trim | 98.9% | 8.6% | 14.7% | 37.3% | 74.0% | **98.3%** |

**배속 차이는 r=0.02(매우 좁은 밴드)에서도 완벽하게 처리된다.** 시도 2·3이 계속
실패하던 부분을 추정 없이 해결했다. 반면 **오프셋 성분은 비율 밴드로 해결되지
않는다** — offset60·trim이 넓은 r을 요구하는 이유다. 비율 대응은 "시작점이 서로
맞다"고 가정하는데, 녹화 시작 시점이 다르면 그 가정이 깨지기 때문이다.

**비율 밴드 + 오프셋 중앙값 제거 (자연 촬영, ±5프레임 내)**

| 쌍 | 기존 | 비율만 r=.10 | 비율만 r=.20 | 비율+오프셋 r=.10 |
|---|---|---|---|---|
| natural1 | 71.8% | 66.7% | 64.1% | **74.4%** |
| natural2 | 61.5% | 33.3% | **61.5%** | 53.3% |

**자연 촬영에서는 기존 대비 유의미한 개선이 없다.** natural1이 74.4%로 소폭
올랐을 뿐이고 natural2는 오히려 나빠지거나 같다.

### 정리 — 왜 밴드 조정만으로는 부족한가

시도 1~4를 종합하면 문제가 두 성분으로 분해된다.

| 성분 | 해결책 | 상태 |
|---|---|---|
| **전역 배속** (길이 비율) | 비율 밴드 (시도 4) | ✅ 해결. 추정 불필요, r=0.02에서도 완벽 |
| **전역 오프셋** (녹화 시작 시점 차이) | 중앙값 제거 | ⚠️ 부분적. 추정이 1단계 DTW에 의존 |
| **국소 오정렬** (발견 1의 원리적 한계) | — | ❌ **미해결** |

핵심은 셋째다. **밴드를 아무리 잘 잡아도, 밴드 안에서 DTW는 여전히 "포즈가 더
비슷한 곳"을 고른다.** 발견 1에서 본 대로 그게 정답보다 더 비슷할 때가 60~67%다.
밴드는 탐색 범위를 제한할 뿐 목적함수를 바꾸지 못한다.

즉 **밴드 튜닝은 전역 성분(배속·오프셋)에는 유효하지만 국소 오정렬에는 무력하다.**
자연 촬영에서 개선이 정체된 이유가 이것이다 — 그 오차의 주성분이 국소 오정렬이기
때문이다.

### 시도 5 — 사용자에게 안무 시작 시점을 입력받기 (유력)

사용자 제안. **오프셋을 알고리즘으로 추정하지 말고 사용자에게 물어본다.**

근거가 강하다. 오프셋 자동 추정은 지금까지 **세 가지 방법이 모두 실패**했다:

| 방법 | 결과 |
|---|---|
| 포즈 DTW 1단계 추정 | natural2에서 기울기 방향조차 반대 (0.87 vs 정답 1.24) |
| 오디오 크로스코릴레이션 | natural2에서 5배 이상 오차 (+0.88초 vs 정답 −4.76초) |
| 비율(정규화 위치) 가정 | 오프셋 성분을 원리적으로 처리 못 함 (시도 4) |

자동 탐지가 어려운 이유도 분명하다 — 사람은 안무 시작 전에 음악을 들으며 리듬을
타거나 자세를 잡는다. 픽셀 변화량이나 움직임 시작만으로는 "안무의 시작"을 판정할
수 없다. **반면 사용자는 그 시점을 안다.** 입력 부담도 작다(영상당 초 단위 하나).

**효과 (앵커에서 구한 정답 오프셋을 "사용자 입력"으로 시뮬레이션)**

| 쌍 | 기존 ±5f | 시작초 입력 + 밴드 ±0.2초 |
|---|---|---|
| natural1 | 71.8% | **89.7%** |
| natural2 | 73.3% | **80.0%** |

최대 오차도 natural1 1.03초 → 0.83초, natural2 0.73초 → 0.37초로 줄었다.

**⚠️ 그러나 입력 오차에 매우 취약하다** (±5프레임 내 %)

| 쌍 | 밴드 | 입력오차 0 | ±0.2초 | ±0.5초 | ±1.0초 |
|---|---|---|---|---|---|
| natural1 | ±0.2초 | 89.7% | 79.5% | **15.4%** | **0.0%** |
| natural1 | ±0.5초 | 74.4% | 74.4% | 71.8% | **0.0%** |
| natural1 | ±1.0초 | 71.8% | 71.8% | 71.8% | 71.8% |
| natural2 | ±0.5초 | 80.0% | 86.7% | 73.3% | **0.0%** |

**밴드를 좁힐수록 성능은 오르지만 입력 오차 허용치가 줄어드는 정면 트레이드오프**가
있다. 그리고 입력 오차가 밴드 폭을 넘으면 **정답 경로가 밴드 밖으로 나가 성능이
0%로 붕괴**한다 — 완만한 저하가 아니라 절벽이다.

**설계 시사점**
- 밴드 폭은 **예상되는 사용자 입력 오차보다 넉넉해야** 한다. 사람이 초 단위로
  찍는 정확도를 ±0.3초로 본다면 밴드는 최소 ±0.5초가 안전하다
  (그 조합에서 natural1 71.8%, natural2 73.3%로 **기존과 동등**)
- 즉 **입력을 받아도 밴드를 안전하게 잡으면 이득이 사라진다.** 이득(89.7%)은
  입력이 거의 정확할 때만 나온다
- UI로 정확도를 높일 수 있다면(프레임 단위 스크러빙으로 시작 지점 지정 등) 좁은
  밴드가 가능해지고 그때 이득이 실현된다. **입력 방식의 정밀도가 이 기능의
  가치를 좌우한다**

**결론**: 방향은 옳고 자동 추정보다 신뢰할 만하다. 다만 "초를 입력받는다"만으로는
부족하고 **입력 정밀도까지 설계해야** 실효가 있다. 미구현으로 남긴다.

### 시도 6 — 정렬 신뢰도 지표 탐색 (실패, 중요한 부정 결과)

"정확도가 낮으면 사용자에게 다시 하라고 안내한다"는 설계를 하려면, 먼저
**GT 없이 정렬 품질을 예측하는 신호**가 필요하다. 앵커 52개(natural1+2)를 정답으로
두고 후보 5개의 예측력을 측정했다.

| 후보 신호 | 정렬오차와의 상관 | 큰오차군(>0.2초) | 작은오차군 |
|---|---|---|---|
| 매칭 지점 포즈오차 | +0.136 | 29.4° | 22.3° |
| 매칭 선명도(margin) | +0.031 | 1.62 | 1.55 |
| 유사 후보 비율(평평함) | +0.260 | 0.086 | 0.077 |
| 유효 관절율 | +0.116 | 0.991 | 0.970 |
| 정면성 | +0.041 | 0.823 | 0.649 |

**전부 예측력이 없다.** 상관계수 0.03~0.26이고 두 군의 평균이 거의 겹친다.

**왜 실패했는지가 중요하다.** 발견 1에서 확인한 실패 양상은 **"불확실한 매칭"이
아니라 "확신에 찬 틀린 매칭"**이다. DTW가 실제로 더 비슷한 포즈를 찾아낸 것이므로,
그 지점에서는 포즈 오차도 낮고 매칭 선명도도 높다. **틀린 매칭이 맞은 매칭보다
오히려 더 좋아 보인다.**

→ **국소 신뢰도 지표로는 원리적으로 감지 불가능하다.** "매칭이 얼마나 확신에
찼는가"를 재는 모든 지표가 무력하다. 이 방향은 접는다.

**설계 방향 전환**: 정렬 오류를 *탐지해서* 재촬영을 안내하는 것은 현재 불가능하다.
대신 두 갈래로 나눈다.

1. **예방** — 시작 시점을 사용자가 직접 정밀하게 지정하게 해서 오프셋 오류가
   애초에 생기지 않게 한다 (시도 5). 프레임 단위 선택 UI가 핵심.
2. **측정 가능한 것만 게이트** — 정렬 품질이 아니라 **영상 자체의 사용 가능성**
   (검출 실패율, 몸통 4점 확보율, 게이트 통과율, 정면성)으로 재촬영을 안내한다.
   이건 신뢰성 있게 측정되며 원인도 사용자가 고칠 수 있다("전신이 나오게",
   "더 밝은 곳에서").

### 영상 품질 지표 — 정상군 분포 (임계값 설정용 기초 데이터)

정렬 품질은 예측 불가하지만(시도 6), **영상 자체의 사용 가능성**은 신뢰성 있게
측정된다. 보유한 영상 8개의 분포:

| 영상 | 검출실패 | 관절유효율 | 몸통4점 | 게이트통과 | 정면성 |
|---|---|---|---|---|---|
| real pro | 0 | 95.5% | 100.0% | 100.0% | 0.646 |
| real user | 0 | 93.3% | 100.0% | 100.0% | 0.641 |
| nat1 pro | 0 | 93.9% | 100.0% | 100.0% | 0.605 |
| nat1 user | 0 | 92.7% | 99.4% | 99.4% | 0.610 |
| **nat2 pro** | 0 | **88.1%** | **96.6%** | 96.6% | **0.413** |
| **nat2 user** | 0 | **85.1%** | **86.6%** | **86.6%** | 0.595 |
| cand1 pro | 0 | 99.2% | 100.0% | 100.0% | 0.603 |
| cand3 pro | 0 | 97.2% | 100.0% | 100.0% | 0.591 |

**natural2가 뚜렷한 이상치다.** 관절 유효율 85~88%(다른 영상 92.7~99.2%),
몸통 4점 확보율 86.6~96.6%(다른 영상 99.4~100%), pro의 정면성 0.413(다른 영상
0.59~0.65). 즉 natural2는 **전신이 자주 안 잡히고 pro가 상당히 측면을 향한다.**

**이것이 앞선 관찰들을 설명한다.** natural2는 계속 성능이 나빴다 —
채점률 31.0%(natural1 72.9%), 오디오 오프셋 추정 실패, 앵커 정렬 ±5f 61.5%.
원인 미상으로 남겨뒀던 것들이 **영상 품질 문제로 상당 부분 설명된다.**
정렬 알고리즘의 한계가 아니라 입력 품질의 문제였을 가능성이 크다.

**→ 품질 게이트의 실효성을 뒷받침하는 근거**다. natural2 같은 영상을 사전에
걸러 재촬영을 안내했다면 이후 문제들이 발생하지 않았을 것이다.

**⚠️ 다만 임계값은 아직 정할 수 없다.** 위 8개는 전부 "분석이 되긴 한" 영상이라
**실패 사례가 없어 경계를 모른다.** 의도적으로 나쁜 영상(전신 잘림 / 매우 어두움 /
측면 촬영)을 각 1개씩 확보하면 정상군-실패군 경계가 드러난다. 그때까지는
임계값 없이 **측정값을 사용자에게 노출**하는 방식이 정직하다.

### 시도 7 — 밴드 폭을 "영상 길이 대비 비율"로 (부정 결과)

시도 4에서 두 가지를 섞어서 평가한 오류를 바로잡은 재검증. 분리하면:

| | 내용 | 시도 4 결과 |
|---|---|---|
| (가) 밴드 **폭**을 길이 비율로 | 60초 영상이면 밴드도 그만큼 넓게 | 미평가 (섞여 있었음) |
| (나) 위치를 **비율로 대응** | 두 영상의 안무 시작·끝이 같은 상대 위치라 가정 | ❌ 실패 (오프셋 처리 불가) |

(가)를 단독 평가하려면 **"오프셋 제거 후 남는 편차가 영상 위치에 따라 커지는가"**
를 보면 된다. 커진다면(누적 드리프트) 비율 밴드가 맞고, 일정하다면(국소 지터)
고정 시간 밴드가 맞다.

**앵커 잔차 분석** (오프셋 중앙값 제거 후)

| 쌍 | 잔차 표준편차 | 최대 \|잔차\| | 잔차–위치 상관 | 앞 1/3 | 중간 | 뒤 1/3 |
|---|---|---|---|---|---|---|
| natural1 (22.9초) | 0.200초 | 1.005초 | **−0.097** | 0.089초 | 0.187초 | 0.078초 |
| natural2 (7.6초) | 0.126초 | 0.333초 | **−0.056** | 0.077초 | 0.074초 | 0.118초 |

**드리프트가 관측되지 않는다.** 위치와의 상관이 두 쌍 모두 **음수**(−0.097, −0.056)로,
뒤로 갈수록 편차가 커지기는커녕 오히려 미세하게 줄어든다. 구간별 평균도 단조
증가하지 않는다(natural1은 중간이 가장 크다).

→ **오프셋만 제거하면 남는 것은 누적 드리프트가 아니라 국소 지터다.** 따라서
밴드 폭은 영상 길이에 비례할 이유가 없고, **고정 시간(초) 기준이 맞다.**
구체적으로 잔차 표준편차가 0.13~0.20초이므로 **±0.5초 밴드면 3σ에 가깝고 충분하다.**

**⚠️ 일반화 한계**: 영상 2개(22.9초, 7.6초 구간)에서만 확인했다. 사용자가 언급한
1분 영상은 우리 데이터의 2.6배 길이라 **누적 드리프트가 그 길이에서도 없다고는
말할 수 없다.** 다만 현재 관측 범위에서는 드리프트 성분이 보이지 않으므로,
비율 밴드를 도입할 근거가 없다.

**결론**: (가)도 채택하지 않는다. 다만 시도 4에서 확인한 대로 **배속 차이가 큰
경우에는 비율 대응이 유효**하므로, 향후 배속 영상을 다루게 되면 재검토할 것.

### 구현 — 안무 구간 지정 (D23) ✅

시도 5의 결론을 정식 기능으로 구현했다. 사용자에게 안무 시작/끝 시점을 받아
그 구간만 추출하고, 전역 오프셋이 제거된 상태이므로 좁은 밴드를 쓴다.

| 파일 | 변경 |
|---|---|
| `src/extract.py` | `start_sec`/`end_sec`로 구간만 추출. 원본 시작 프레임을 `meta['source_start_frame']`에 보존 |
| `src/main.py` | `--pro-start-sec` / `--user-start-sec` / `--pro-end-sec` / `--user-end-sec` / `--band-sec` |
| `tools/eval_alignment.py` | 캐시 키에 구간 반영 |

설계 포인트:
- **밴드 자동 축소** — 구간을 지정하면 `--band-sec` 기본 0.5초가 적용된다
  (시도 7의 잔차 σ 0.13~0.20초의 3σ 수준). 미지정 시 기존 `--window 15` 유지
- **원본 인덱스 보존** — 잘라낸 뒤 프레임 번호는 사용자에게 무의미하므로
  `details`에 `user_frame_src` / `user_t_src`(원본 영상 기준)를 함께 기록
- 프레임 탐색은 `cap.set(POS_FRAMES)` 대신 읽고 건너뛰기 — 코덱에 따라 키프레임으로
  붙어 부정확할 수 있고, 비싼 포즈 추정은 어차피 건너뛰므로 손해가 작다

**구현 중 발견한 버그 — 구간 지정 시 psi를 꺼야 한다**

검증에서 natural2의 앵커 커버리지가 15개 중 10개로 줄었다. 구간 밖 앵커는 0개인데도
줄어서 원인을 파보니, **psi(끝점 완화)가 확정한 구간의 양 끝을 다시 건너뛰고
있었다.** psi는 "안무 구간이 어디인지 모를 때" 쓰는 장치인데 구간을 이미 확정했으면
역할이 중복되고 오히려 해가 된다.

| natural2 | 앵커 커버 | 중앙 오차 | ±5f 내 | 최대 오차 |
|---|---|---|---|---|
| psi 유지 | 10개 | 0.058초 | 70.0% | 1.25초 |
| **psi 끔** | **14개** | 0.067초 | **78.6%** | **0.27초** |

→ 구간 지정 시 psi를 자동으로 끄도록 수정 (`--keep-psi-on-trim`으로 복원 가능).

**최종 검증 (앵커 GT)**

| 쌍 | 설정 | n | 중앙 오차 | ±2f | ±5f | 최대 |
|---|---|---|---|---|---|---|
| natural1 | 기존 | 39 | 0.100초 | 41.0% | 71.8% | 1.03초 |
| natural1 | **구간지정+psi끔** | 38 | 0.100초 | 42.1% | **78.9%** | **0.60초** |
| natural2 | 기존 | 13 | 0.100초 | 46.2% | 61.5% | 1.23초 |
| natural2 | **구간지정+psi끔** | 14 | 0.067초 | **64.3%** | **78.6%** | **0.27초** |

**두 쌍 모두 개선됐고, 특히 최대 오차가 크게 줄었다**(1.03→0.60초, 1.23→0.27초).
최악의 오정렬이 줄어든 것이 평균 개선보다 중요하다 — 사용자에게 명백히 틀린
피드백을 주는 사례가 그만큼 준다는 뜻이기 때문이다.

파이프라인 전체 효과도 확인됐다 — natural1 기준 고정 오프셋 +3.65초 → −0.03초,
채점률 72.9% → 100%.

**⚠️ 한계**: 이 검증은 앵커에서 뽑은 시작점을 "사용자 입력"으로 대신 쓴 것이다.
실제 사용자가 그만큼 정확히 지정할 수 있는지는 UI 정밀도에 달렸고(시도 5의
입력 오차 민감도 참고), 아직 검증되지 않았다.

### 시도 8 — 각속도를 DTW 입력에 추가 (D24) ✅ 채택

사용자 제안에서 출발. "동작을 완전히 틀리면 포즈 매칭이 실패하는 건 당연하지만,
그동안 벡터값이 오르내리는 **흐름과 주기**는 남아 있으니 그 패턴으로 맞출 수
있지 않을까"라는 착안.

핵심 통찰은 **"포즈가 무엇인가"가 아니라 "언제 움직임이 일어났는가"** 로 맞추는
것이다. 같은 음악에 맞춰 춘다면 움직임의 악센트(치고·멈추고·방향 바꾸는 순간)는
포즈가 틀려도 유지된다. 이는 시도 6에서 확인한 원리적 한계
("포즈 유사도 ≠ 안무 구조")를 우회할 수 있는 **독립적인 신호**다.

그리고 이 방식은 **오디오가 필요 없다** — 관절 각속도에서 움직임 악센트를 뽑으면
영상만으로 같은 정보를 얻는다. 오디오 유무에 의존하던 기존 방향의 약점을 피한다.

**시도 8-a. 움직임 포락선 상호상관으로 오프셋 추정** ❌

각속도 평균을 오디오 온셋 포락선처럼 써서 전역 오프셋을 추정:

| 쌍 | 추정 | 정답 | 오차 |
|---|---|---|---|
| natural1 | +1.77초 | +3.65초 | 1.88초 |
| natural2 | −5.43초 | −4.76초 | 0.68초 |

오차가 커서 오프셋 추정 수단으로는 부적합. (오프셋은 D23의 사용자 입력으로 해결됨)

**시도 8-b. 자기상관으로 박자 주기 추정** ❌

| 쌍 | pro 주기 | user 주기 | 비율 |
|---|---|---|---|
| natural1 | 0.300초 (200 BPM) | 0.967초 (62 BPM) | 3.22 |
| natural2 | 0.458초 (131 BPM) | 0.300초 (200 BPM) | 0.66 |

같은 안무인데 템포 추정이 3배 이상 어긋난다. 자기상관 피크값도 0.29~0.38로 낮아
**뚜렷한 주기 자체가 없다.** 스트릿댄스 동작이 오디오 비트만큼 규칙적으로 반복되지
않기 때문으로 보인다. → 명시적 박자 추정은 접는다.

**시도 8-c. 각속도를 DTW feature에 직접 추가** ✅ **채택**

박자를 명시적으로 추정하는 대신, 각속도를 자세와 함께 DTW 입력에 넣어 **DTW가
알아서 타이밍 정보를 쓰게** 한다. 각도별 표준편차로 정규화해 스케일을 맞춘 뒤
가중치를 곱한다.

| 쌍 | 입력 | ±2f | ±5f | 최대 |
|---|---|---|---|---|
| natural1 | 자세만 (기존) | 44.7% | 78.9% | 0.60초 |
| natural1 | 속도만 | 42.1% | 71.1% | 0.90초 |
| natural1 | **자세+속도 w=0.5** | **57.9%** | **81.6%** | 0.73초 |
| natural1 | 자세+속도 w=2.0 | 50.0% | 81.6% | 0.90초 |
| natural2 | 자세만 (기존) | 57.1% | 92.9% | 0.27초 |
| natural2 | 속도만 | 28.6% | 71.4% | 0.32초 |
| natural2 | **자세+속도 w=0.5** | **64.3%** | **100.0%** | **0.17초** |
| natural2 | 자세+속도 w=2.0 | 21.4% | 71.4% | 0.32초 |

**두 쌍 모두 w=0.5에서 최선**이다. natural2는 ±5프레임 내 100%를 달성했다.

**가중치가 결정적이다.** 속도만 쓰면 오히려 나빠지고(±2f 28.6%), 가중치가 크면
(w=2.0) 역시 나빠진다. **자세가 주 신호, 속도는 보조**라는 구조가 맞다.

**합성 변형본 회귀 확인** — 모두 유지 (offset60/speed0.90/speed1.10/local0.50
전부 100%, trim 98.9%). 자연 촬영만 개선되고 손해는 없다.

→ `FeatureSet.alignment_matrix(velocity_weight=0.5)`로 **기본 적용**.

### 남은 방향

- **오디오 기반 오프셋의 재평가.** 위 순환을 끊을 수 있는 유일한 독립 신호다.
  음악은 사용자가 동작을 틀려도 변하지 않으므로, 포즈 유사도와 독립적인 시간
  기준을 제공한다. 다만 natural2에서 오디오 추정이 틀렸던 전례가 있어
  (실제 −4.756초 vs 오디오 +0.882초) 신뢰도 판정을 강화해야 한다.
- 밴드 폭을 단일 값이 아니라 **국소 속도 편차 예상치**에 맞춰 결정
- (b)가 원리적 한계라면, 정렬 신뢰도가 낮은 구간을 **채점에서 제외하고 사용자에게
  "이 구간은 평가하지 않음"으로 표시**하는 방향도 검토 가치 있음

## Phase 5 — 피드백 기능 (`src/feedback.py`) ✅

프레임별 각도 오차를 사용자가 읽을 수 있는 형태로 변환한다.

### 출발점의 문제 (실측)

`compare_sequences` 출력을 그대로 보면:

```
user  7.77s ↔ pro  4.07s | 평균 32.8도 | r_forearm 110도, r_elbow_bend 93도, ...
... 0.27초 간격으로 87개
```

| 문제 | 근거 |
|---|---|
| **양이 과함** | 23초 영상에 87개, 0.27초 간격 |
| **구간이 안 보임** | `l_forearm`이 8.3/8.6/8.9초 연속 — 한 동작인데 3건으로 보임 |
| **방향이 없음** | "팔꿈치 96도 차이"만으로는 굽혀야 할지 펴야 할지 모름 |
| **부위 간 비교 불가** | 전완이 항상 상위(중앙 29.9도 vs 몸통 9.1도) — 가동 범위가 넓어서지 더 못해서가 아님 |

### 설계 결정 (사용자 협의)

| 항목 | 결정 |
|---|---|
| 단위 | **구간별**. 연속 프레임을 묶고 구간 사이 최소 간격 |
| 점수 | **폐기.** 대신 **틀린 동작 개수**를 센다. 환산 상수가 임의값이라 절대값에 의미가 없음 |
| 신뢰도 낮은 구간 | **평가하지 않고 따로 모음** ("확인 어려움") |
| 정규화 기준 | **(b) 영상 자체의 부위별 분포** — 사람·안무마다 가동 범위가 달라 고정 상수보다 안전 |

### 구현

1. **부위별 구간 병합** — 같은 부위가 `max_gap_sec`(0.5초) 이내로 연속되면 한 구간
2. **부위별 정규화** — 그 영상의 부위별 오차 중앙값을 1.0으로 두는 `severity`
3. **방향 부여** — `pairwise_error`가 **부호 있는 차이**(사용자 − 기준)를 함께 반환하도록
   확장하고, 부위별 문구 쌍으로 "더 펴세요 / 더 굽히세요" 생성
4. **신뢰 불가 분리** — 프레임 평균 오차 ≥ 90도면 지적하지 않음.
   근거: natural1 분포에서 p95=49도인데 p99에서 119도로 급격히 튀고 최대 178도.
   178도는 물리적으로 정반대 방향이라 같은 동작을 비교한 결과로 보기 어렵다
   (시도 6의 되먹임 문제 — 사용자가 크게 틀리면 정렬 자체가 실패할 수 있음)
5. **신체 그룹 병합** — 아래 참조

### 구현 중 발견 — 부위별 구간만으로는 부족했다

1차 구현 후 상위 5개가 이렇게 나왔다:

```
1. [ 8.6~11.5s] 오른쪽 정강이     2. [23.8~26.2s] 오른쪽 위팔
3. [ 8.8~11.0s] 오른쪽 무릎       4. [ 8.3~11.8s] 왼쪽 정강이
5. [29.1~29.9s] 오른쪽 무릎
```

**상위 5개 중 4개가 8.3~11.8초 한 구간에 몰렸다.** 측정해보니 한 시점에 평균 5.4개,
최대 11개 부위가 동시에 걸린다. 같은 순간의 다리 동작 하나를 정강이·무릎·좌·우로
쪼개서 네 번 말하는 셈이다.

→ **신체 그룹**(왼팔/오른팔/왼다리/오른다리/상체)으로 묶고, 시간대가 겹치면
합친다. 대표 문구는 그룹 내 가장 심각한 부위의 것을 쓴다.

## 실행 환경 메모

- `venv/`는 정상 동작 확인됨 (Python 3.10.18, mediapipe 0.10.21,
  ultralytics 8.3.155, dtaidistance 2.3.13 전부 import 성공)
- **신규 의존성 3개를 추가했다** (transformers 5.16.1 / onnxruntime 1.23.2 /
  rtmlib 0.0.16). CLAUDE.md가 경고하는 버전 붕괴를 피하려고,
  `pip install --dry-run --report -`로 **기존 고정 버전이 하나도 안 바뀌는 것을
  먼저 확인**한 뒤 설치했고 사후에도 import를 재확인했다. 전부 신규 설치였고
  업그레이드는 0건이다. `requirements.txt`에 반영됨
- 개발/실험 머신: Apple M2 16GB. `pose_yolo.py`가 이미 `device='mps'` 사용 중
- 배포 후보: 맥미니 M1 16GB 홈서버. 분석이 비동기 처리라 실시간 제약이 없어
  무거운 모델도 현실적. 필요 시 프레임 서브샘플링(30fps → 10~15fps)으로
  연산량을 1/2~1/3로 줄일 수 있음 (단 DTW 시간 해상도도 같이 낮아짐)
- 영상 스펙: `data/videos/real/` 1080x1920, 30.000fps, 393프레임, 13.1초 /
  `candidates/candidate1/` 360x640, 29.970fps, 450프레임, 15.0초
- **dtaidistance의 C 확장은 비활성 상태**다 (`libomp.dylib` 없음). 순수 파이썬
  폴백으로 도는데, 393x393 dim=51 기준 `warping_path`가 0.07초라 현재 규모에서는
  문제 없다. 영상이 길어지면 `brew install libomp`로 가속 가능
- **ultralytics가 "Apple MPS known Pose bug, device=cpu 권장" 경고를 띄우지만,
  실측 결과 MPS와 CPU의 키포인트가 완전히 동일했다** (27프레임 459관절,
  최대 차이 0.00px). 이 조합에서는 영향이 없으므로 `device='mps'`를 유지한다
- 신뢰도 임계값 근거 — `real` 기준영상 40프레임 샘플의 분포:
  YOLO-pose conf는 중앙값 0.971(p25=0.931)로 매우 확신하는 반면,
  MediaPipe visibility는 중앙값 0.693(p25=0.567)에 0.4~0.7 구간에 큰 덩어리가
  있다. 임계 0.7이면 YOLO는 91.3%가 남지만 MediaPipe는 49.2%만 남는다.
  **공통 임계값을 쓸 수 없어** 백엔드별로 분리했다 (`DEFAULT_CONF_THRESH`)
