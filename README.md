## 1. 프로젝트 소개

### 배경

스트릿댄스 동아리 팀장으로서, 정기 연습 시간 외에는 후배들이 자기 자세를 점검할
방법이 없다는 문제를 봤습니다. 처음 다뤄보는 비전 기술로, 프로 댄서 영상과 비교해
어디가 어긋났는지 알려주는 서비스를 만들었습니다.

### 문제를 세 축으로 나눴습니다

"두 영상을 비교한다"는 한 문장이지만, 실제로 성립하려면 세 가지가 각각 맞아야 합니다.

| 축 | 질문 | 안 맞으면 |
|---|---|---|
| **① 탐지** | 관절이 제대로 잡히는가 | 애초에 비교할 좌표가 틀림 |
| **② 정렬** | 서로 다른 시간대의 같은 동작이 매핑되는가 | 다른 동작끼리 비교하게 됨 |
| **③ 표현** | 촬영 조건 차이가 동작 차이로 오인되지 않는가 | ①②가 완벽해도 최종 수치가 무의미 |

③은 뒤늦게 추가한 축입니다. 처음에는 ①②만 생각했는데, **카메라 거리·위치·기울기
차이가 그대로 "동작 오차"로 계산되고 있다**는 걸 측정으로 확인하고 나서 별도 축으로
분리했습니다 (→ [3.3](#33-좌표-대신-관절-각도로-비교)).

## 2. 기술 스택 · 구조

| 영역 | 기술 | 비고 |
|---|---|---|
| Frontend | React 19, Vite | 영상 트림 UI, 결과 화면 |
| API Server | Spring Boot 3.4, Java 17 | 인증·권한·작업 조율 |
| AI Server | FastAPI, Python 3.10 | 포즈 추출·정렬·피드백 생성 |
| Pose Estimation | **YOLO-pose** (`yolov8n-pose`) | 4계열 비교 후 선정 → [3.4](#34-모델-선정--예측이-빗나간-기록) |
| 시계열 매칭 | DTW (`dtaidistance.dtw_ndim`) | 시작 시점·박자 차이 해결 |
| 인증 | Spring Security, JWT, OAuth2 (카카오·네이버) | httpOnly 쿠키 |
| 저장소 | Cloudflare R2 (S3 호환) | presigned URL, egress 무료 |
| 검증 | 합성 변형본 dense GT, pycocotools | → [3.1](#31-먼저-정답을-만들었습니다) |

### 디렉터리 구성

```
├── web-service/
│   ├── frontend/        React 19 + Vite
│   └── api-server/      Spring Boot — 인증·권한·작업 조율
├── ai-server/
│   ├── engine/          model-research에서 이식한 분석 엔진
│   └── main.py          FastAPI — 분석 전용, 아무것도 보관하지 않음
├── model-research/      연구·검증 코드 (방법론 실험)
└── deploy/              Nginx·systemd·launchd 설정과 배포 스크립트
```

`model-research`에서 검증한 방법론이 `ai-server/engine/`으로 이식되는 구조입니다.
두 쪽의 엔진 파일은 import 경로만 다르고 **내용이 동일**하게 유지됩니다.

### 서비스 구조

무거운 일을 각자 잘하는 곳으로 나눈 것이 핵심입니다.

```
브라우저 ──HTTPS──> Cloudflare ──> EC2 (t4g.small)
                        │           ├─ Spring  : 인증·권한·URL 발급
                        │           └─ Postgres
                        │
                        ├──> R2    : 영상 원본 + 결과 이미지
                        │      ↑ presigned URL로 직접 업로드·다운로드
                   Tailscale
                        │
                        └──> 맥미니 : FastAPI — 포즈 추출·정렬 (공인 IP 없음)
                       Fedora Asahi Remix (Apple Silicon + Linux, aarch64)
```

| 결정 | 이유 |
|---|---|
| **영상이 EC2를 지나가지 않음** | 브라우저가 R2로 직접 올리고 맥미니가 R2에서 직접 받습니다. 수십 MB 파일이 작은 인스턴스의 대역폭·디스크를 쓰지 않고, Cloudflare 프록시의 요청 본문 100MB 제한도 거치지 않습니다 |
| **분석은 맥미니** | 포즈 추출은 CPU를 1분 넘게 씁니다. 이걸 EC2에서 하면 인스턴스를 훨씬 키워야 합니다 |
| **R2 (S3 아님)** | egress 요금이 0입니다. 이 서비스에서 가장 큰 트래픽이 맥미니의 영상 다운로드와 사용자의 결과 조회인데, S3였다면 그 둘이 곧바로 비용이 됩니다 |
| **맥미니에 저장소 키를 주지 않음** | Spring이 요청마다 짧은 presigned URL만 발급합니다. 집에 있는 홈서버가 뚫려도 얻을 수 있는 것이 곧 만료될 URL 몇 개뿐입니다 |

### 처리 흐름

분석에 1~2분이 걸려 HTTP 요청을 붙잡고 있을 수 없으므로 **비동기 + 폴링**입니다.

```
1. 업로드    브라우저 → (presigned PUT) → R2          ※ 백엔드를 거치지 않음
2. 구간 지정  안무 시작 시각을 표시 (타임스탬프만 저장, 재인코딩 없음)
3. 분석 요청  POST /practice-logs/{id}/analyze → 202 즉시 반환
4.           Spring → (Tailscale) → 맥미니 → R2에서 영상 다운로드
5.                                        → 포즈 추출 · DTW 정렬 · 구간 피드백
6.                                        → (presigned PUT) 결과 이미지 R2 업로드
7. 폴링      GET /practice-logs/{id} → status가 COMPLETED가 되면 결과 표시
```

**결과물 URL은 저장하지 않고 조회할 때마다 새로 만듭니다.** presigned URL은
만료되므로 DB에 넣으면 얼마 못 가 열리지 않습니다. DB에는 객체 키만 둡니다.

## 3. 핵심 구현

### 3.1 먼저 "정답"을 만들었습니다

**문제**

기존 코드는 점수를 출력했지만, **그 점수가 맞는지 확인할 방법이 없었습니다.**
"정렬이 잘 됐다"고 말하려면 "원래 어디에 정렬됐어야 하는가"라는 정답이 필요한데
그게 없었습니다. 정답 없이 고치는 건 감으로 고치는 것이라, 여기부터 만들었습니다.

**해결 — 정답을 아는 테스트 데이터를 합성**

원본 영상에서 **시간축을 결정적으로 변형한 사본**을 만들었습니다. 제가 만든 변형이니
"변형본 프레임 i는 원본 몇 번 프레임에서 왔는지"를 **모든 프레임에 대해** 정확히
알 수 있습니다. 사람이 찍은 앵커 10~15개짜리 sparse 정답보다 훨씬 촘촘한 GT입니다.

| 변형 | 시뮬레이션하는 상황 |
|---|---|
| `offset` | 녹화를 늦게 시작함 |
| `speed` | 전체적으로 빠르거나 느리게 춤 |
| `local` | 중간 한 구간만 느려짐 (DTW가 진짜 필요한 케이스) |
| `trim` | 안무의 일부만 춤 |
| `zoom`/`shift`/`roll` | 카메라 거리·위치·기울기 차이 (시간축은 그대로) |
| `reencode` | **대조군** — 아무 변형 없이 재인코딩만 |

마지막 `reencode` 대조군이 중요했습니다. 다른 변형에서 나온 오차가 **"변형 때문인지
포즈 추정 노이즈 때문인지"** 를 구분하려면 노이즈 바닥을 알아야 했기 때문입니다.

**한계도 같이 적어둡니다** — 변형본은 원본과 같은 영상에서 나왔으므로 두 포즈
시퀀스가 거의 동일합니다. 따라서 이 GT는 "정렬 기계가 의도대로 작동하는가"는
증명하지만 **"다른 댄서 사이에서도 정렬되는가"는 증명하지 않습니다.**

### 3.2 DTW 정렬 — 라이브러리 API를 잘못 쓰고 있었습니다

**증상**

3.1의 GT로 재보니, 2초(60프레임) 앞부분이 잘린 영상에서 **정렬 오차 중앙값이 정확히
2.000초**로 나왔습니다. 오차가 오프셋 값과 정확히 일치한다는 건, 시간 어긋남을
**전혀 감지하지 못하고 프레임 i를 i에 그대로 매칭**하고 있다는 뜻이었습니다.

**원인**

`dtaidistance.dtw.distance()`는 **1차원 스칼라 시계열 전용** API인데, 여기에
`(프레임수 × 51,)` 로 통짜 flatten한 다차원 데이터를 넣고 있었습니다.
그러면 프레임 경계가 사라져서 "5번 프레임의 y좌표"와 "6번 프레임의 x좌표"를
정렬하는 꼴이 됩니다. `window=7`도 "7프레임 허용"이 아니라 "숫자 7개 허용"
(≈0.14프레임)으로 해석되어 사실상 정렬 여유가 없었습니다.

**해결** — 다변량을 지원하는 `dtw_ndim`으로 교체. 프레임 하나를 하나의 점으로 취급합니다.

**결과 (동일 GT, offset 변형)**

| 구현 | 대응된 프레임 | 중앙 오차 | ±2프레임 내 | 소요 |
|---|---|---|---|---|
| 기존 (1D flatten) | 203/333 (61%) | 2.000초 | 0.0% | 60.4초 |
| **개선 (`dtw_ndim`)** | **333/333 (100%)** | **0.000초** | **97.6%** | **0.07초** |

**추가로 두 가지를 더 고쳤습니다**

- **0으로 채우던 결측 관절** → 명시적 유효성 마스크로 전환.
  기존에는 가려진 관절을 `0`으로 채웠는데, 두 영상 모두 `0`이면 거리도 `0`이 되어
  **"완벽하게 일치"로 계산**됐습니다. 가려질수록 점수가 오르는 역전이었습니다.
- **끝점 강제 완화 (psi).** 일반 DTW는 경로를 (처음, 처음)~(끝, 끝)으로 강제합니다.
  사용자가 안무 일부만 추면 대응 없는 구간까지 억지로 이어붙여 정렬이 망가집니다.

  | 안무 일부만 춘 영상 | 평균 오차 | ±5프레임 내 |
  |---|---|---|
  | 끝점 강제 (기존) | 0.446초 | 83.1% |
  | **psi 완화** | **0.002초** | **99.4%** |

  전체가 정상 대응하는 경우에도 손해가 없어서 기본값으로 켰습니다.

### 3.3 좌표 대신 관절 각도로 비교

**문제 — 좌표는 동작이 아니라 "프레이밍"을 재고 있었습니다**

시간축은 그대로 두고 **촬영 조건만 바꾼** 변형본(3.1)으로 측정했습니다. 시간이
동일하므로 프레임 i를 i와 직접 비교하면, 남는 오차는 전부 "촬영 조건 차이를 못
걸러낸 양"입니다.

| 변형 | 좌표 기반 (대조군 대비) | 각도 기반 (대조군 대비) |
|---|---|---|
| 재인코딩만 (대조군) | 1x | 1x |
| 줌 1.3배 | **47.5x** | 5.4x |
| 위치 이동 | **127.3x** | 4.8x |
| 카메라 8° 기울임 | **22.4x** | 5.1x |

위치 이동의 경우, 제가 적용한 변위를 계산하면 `0.1047`인데 측정된 좌표 오차도
**`0.1047`로 소수점 넷째 자리까지 일치**했습니다. 좌표 feature가 동작 차이가 아니라
프레이밍 차이를 그대로 재고 있었다는 증거입니다.

반면 각도 오차는 **변형 종류와 무관하게 일정**했습니다. 좌표 영향이 5.7배 차이 나는
세 변형에서 각도가 거의 같다는 건, 남은 오차가 변형 때문이 아니라는 뜻입니다.

**구현**

- 팔·다리 분절 방향각을 **몸통 축 기준 상대 각도**로 계산 → 카메라 기울기가 상쇄됩니다
  (몸통과 팔이 같이 회전하므로 상대 각도는 불변)
- 몸통 기울기는 절대 기준이 필요한데, **영상별 몸통 축 중앙값을 그 영상의 "수직"으로
  정의**해 자가 보정했습니다. 카메라 기울기는 분포 전체를 일정하게 밀어내는 상수
  오프셋이라 중앙값을 빼면 상쇄됩니다. **촬영 가이드가 필요 없습니다.**
  → 실제로 8° 기울인 영상에서 몸통 기울기 오차가 1.0°에 그쳤습니다.
- 각도는 순환량(−179°와 +179°는 2° 차이)이므로 DTW 입력은 `(cos, sin)`으로 인코딩

**부수 효과** — 리포트가 해석 가능한 형태가 됐습니다. 기존에는 관절 번호와 정규화된
거리값(`joint 8`, `0.34`)이 나와서 사람이 읽을 수 없었는데, 이제 부위 이름과 각도
차이(`r_elbow_bend`, `128°`)로 나옵니다. 사용자 피드백 문구로 바로 쓸 수 있는
형태입니다.

### 3.4 모델 선정 — 예측이 빗나간 기록

정답 라벨이 없어도 잴 수 있는 지표를 설계했습니다. 그중 핵심은 **뼈 길이 안정성**입니다.

> 사람 몸은 강체라 전완 길이가 프레임 사이에 갑자기 튀면 그건 동작이 아니라 추정
> 오류입니다. 특히 겹침 구간에서 모델이 가려진 관절을 지어내면 여기서 잡힙니다.
> 즉 **라벨 없는 겹침 오류 탐지기**입니다. (투영 단축은 부드럽게 변하므로 프레임 간
> 급변만 보면 단축과 오류가 구분됩니다.)

**결과 (같은 영상 393프레임)**

| 모델 | 뼈 불안정 ↓ | fps |
|---|---|---|
| yolov8n-pose (기존) | 0.0143 | 26.0 |
| **yolo11x-pose** | **0.0127** | 5.7 |
| MediaPipe Full | 0.0189 | 29.1 |
| ViTPose-base | 0.0136 | 6.0 |
| RTMPose-l | 0.0150 | 3.6 |

**예측이 틀렸습니다.** 시작할 때 "RTMPose가 본선 유력, ViTPose가 정확도 천장"이라고
봤는데 **둘 다 yolo11x를 이기지 못했습니다.** RTMPose-l은 기존 yolov8n보다도 뼈
안정성이 나빴습니다.

**서브샘플링이 결론을 뒤집었습니다**

yolo11x는 품질 1위지만 4.6배 느려서 채택하기 어려웠는데, 프레임을 띄엄띄엄 처리하면
어떨지 재봤습니다.

| 처리 fps | 연산량 | 정렬 평균 오차 | ±5프레임 내 |
|---|---|---|---|
| 30 | 100% | 0.003초 | 100% |
| **10** | **33%** | **0.030초** | **100%** |
| 5 | 17% | 0.049초 | 100% |

오차가 **해상도 하한(k/2 프레임)을 그대로 따라갑니다.** 즉 성능 저하의 대부분이
알고리즘 붕괴가 아니라 시간 해상도의 원리적 한계입니다.

| 구성 | 원본 프레임당 실효 비용 | 뼈 불안정 |
|---|---|---|
| yolov8n @ 30fps | 38.4ms | 0.0143 |
| **yolo11x @ 10fps** | **58.9ms** | **0.0127** |

**"무거운 모델은 비싸서 못 쓴다"는 전제가 서브샘플링과 결합하면 성립하지 않았습니다.**

**단, 채점까지 띄엄띄엄 하면 안 됩니다.** 정렬과 달리 채점은 프레임을 건너뛰면
큰 오차 순간을 놓쳐서 **점수가 낙관적으로 편향**됩니다 (5fps에서 46.4점 → 54.0점).

여기서 한 번 더 확인이 필요했습니다. 프레임을 건너뛰면 채점 대상 수도 455개 →
47개로 줄어드는데, **표본이 작아지면 최대값은 그것만으로도 낮아지기** 때문입니다.
그래서 전체 프레임의 오차 분포에서 같은 개수만 무작위로 뽑는 대조군(1000회)을
만들어 분리했습니다.

- 처음 눈에 띈 "최대 오차 −54.8%"는 **대부분 표본 축소 효과**였습니다 (대조군 편차
  ±17에 묻힘). 제 경보가 과했습니다.
- 반면 **p90은 모든 배수에서 일관되게 약 2σ 아래**로, 표본 크기로 설명되지 않는
  실제 정보 손실이었습니다 (10~22% 과소평가).

→ **정렬은 띄엄띄엄, 채점은 촘촘하게** 분리하는 게 맞다는 결론입니다.

### 3.5 실제 두 사람 사이에서의 검증 — 각도 방식이 이겼습니다

3.3까지의 각도 vs 좌표 비교는 전부 **같은 사람의 같은 영상**을 변형한 것이었습니다.
"정렬 기계가 의도대로 작동하는가"는 증명했지만 "실제 다른 두 사람 사이에서도
통하는가"는 증명하지 못한 채 남아 있었습니다. 이걸 확인하려면 **사람이 직접
대응 시점을 표시한 정답(앵커)** 이 필요했고, 실제 촬영 영상 2쌍(조명·거리·밝기를
의도적으로 다르게 촬영)에 앵커 39개, 15개를 라벨링해 확인했습니다.

| 쌍 | feature | 중앙 오차 | ±5프레임 내 |
|---|---|---|---|
| 쌍 A (n=39) | **각도** | **0.100초** | **71.8%** |
| 쌍 A (n=39) | 좌표 | 3.668초 | 0.0% |
| 쌍 B (n=15) | **각도** | **0.100초** | **66.7%** |
| 쌍 B (n=15) | 좌표 | 2.668초 | 0.0% |

**좌표 기반은 사실상 정렬을 전혀 못 했습니다.** 좌표의 오차가 그 쌍의 고정
오프셋(녹화 시작 시점 차이)과 거의 같은 크기였는데, 이는 시간 워핑을 전혀 안
하고 프레임을 순서대로 그대로 매칭했다는 뜻입니다. 카메라 거리·밝기가 다른
두 사람의 좌표를 직접 비교하니 실제 포즈 유사도 신호가 촬영 조건 차이에
완전히 묻힌 것으로 보입니다.

**각도 기반은 서로 다른 안무·다른 촬영 조건의 두 쌍에서 독립적으로 일관된
결과**(±5프레임 내 67~72%)를 보였습니다. 우연으로 보기 어려운 재현성입니다.

다만 완벽하지는 않습니다 — ±2프레임 내는 41~47%에 그쳤고, 오차가 큰 앵커는
두 쌍 모두 영상 초반에 몰려 있었습니다. 원인은 아직 못 찾았습니다(안무 초반의
포즈가 더 모호해서인지, 사용자가 동작을 틀리게 실행한 지점과 겹쳐서인지 등
후보만 세워둔 상태입니다).

**부수 발견 — 오디오 사전 정렬(5.7 검토했던 기능)의 검증**: 앵커로 "진짜"
오프셋을 계산할 수 있게 되면서, 오디오 기반 추정과 대조했습니다. 한 쌍에서는
오디오·포즈 두 방법이 실제값과 0.01초 이내로 일치했지만, 다른 한 쌍에서는
**오디오 추정이 완전히 틀렸습니다**(부호까지 반대, 5배 이상 차이). 신뢰도
임계값을 통과했는데도 틀렸다는 뜻이라, 오디오 정렬을 단독으로는 신뢰할 수
없다는 게 확인됐습니다. 파이프라인에 연결하지 않은 기존 판단이 맞았던
셈입니다.

### 3.6 정렬을 더 밀어붙였습니다 — 시작 시점과 움직임 속도

3.5에서 각도 방식이 이겼지만 ±2프레임 내는 41~47%에 그쳤습니다. 오차가 큰 지점이
영상 초반에 몰리는 패턴도 있었습니다. 원인을 파고들어 두 가지를 개선했습니다.

**원인 진단 — DTW는 실패한 게 아니라 목적함수에 충실했습니다**

앵커마다 "정답 지점의 포즈 오차"와 "DTW가 고른 지점의 포즈 오차"를 비교했더니,
**DTW가 정답보다 포즈가 더 비슷한 곳을 고른 비율이 60~67%** 였습니다. 그리고
오차가 큰 지점은 정답 지점의 포즈 오차 자체가 높았습니다(35° vs 평균 27.6°) —
**사용자가 그 동작을 실제로 크게 틀린 지점**이었습니다.

즉 "포즈 유사도 ≠ 안무 구조"라는 원리적 한계입니다. 여기서 중요한 함의가 나옵니다:
**사용자가 틀릴수록 정렬이 어긋나고, 정렬이 어긋나면 채점도 틀립니다.** 잘 추는
사람에게는 정확하고 못 추는 사람에게는 부정확해지는 구조인데, 정작 후자가 이
서비스의 주 사용자입니다.

**개선 ① 안무 시작 시점을 사용자에게 받기**

녹화 시작 시점 차이(오프셋)를 자동으로 추정하려 했지만 **세 방법이 모두
실패**했습니다 — 포즈 기반 DTW(부호조차 반대), 오디오 크로스코릴레이션(5배 오차),
비율 가정(원리적으로 처리 불가). 자동 탐지가 어려운 이유도 분명했습니다. 사람은
안무 시작 전에 음악을 들으며 리듬을 타거나 자세를 잡습니다.

그래서 **사용자에게 물어보는 쪽**으로 방향을 틀었습니다. 영상당 초 단위 숫자
하나면 되고, 사용자는 그 시점을 압니다.

**개선 ② 각속도를 정렬 신호에 추가**

포즈가 틀려도 **움직임의 타이밍**(언제 치고 멈추고 방향을 바꾸는가)은 음악에 맞춰
유지됩니다. 관절 각속도를 DTW 입력에 보조 성분으로 넣었습니다. 오디오가 필요 없어
"음원이 없을 수도 있다"는 제약도 피합니다.

가중치는 실측으로 정했습니다 — **0.5에서 두 쌍 모두 최선**이고, 속도만 쓰면
오히려 나빠집니다(±2프레임 내 28.6%). 자세가 주 신호, 속도는 보조입니다.

**결과 (앵커 기준)**

| 단계 | 쌍 A ±5프레임 | 쌍 B ±5프레임 | 쌍 B 최대 오차 |
|---|---|---|---|
| 좌표 기반 (최초) | 0% | 0% | — |
| 각도 전환 (3.3) | 71.8% | 61.5% | 1.23초 |
| + 시작 시점 지정 | 78.9% | 78.6% | 0.27초 |
| **+ 각속도** | **81.6%** | **100%** | **0.17초** |

**최대 오차가 크게 줄어든 것**이 평균 개선보다 중요합니다. 사용자에게 명백히
틀린 피드백을 주는 사례가 그만큼 줄어든다는 뜻이기 때문입니다.

> 시작 시점 입력은 **입력 정밀도가 이득을 좌우**합니다. ±0.5초 오차가 있으면
> 이득이 사라지고, 밴드보다 오차가 크면 성능이 0%로 붕괴합니다(절벽형).
> 그래서 텍스트로 초를 받는 방식이 아니라 **프레임 단위 선택 UI**가 전제입니다.

### 3.7 피드백 — 수치를 사람 말로

여기까지가 "얼마나 다른가"를 재는 과정이고, 마지막이 그걸 **사용자가 읽을 수 있는
지적**으로 바꾸는 단계입니다. 분석 결과를 그대로 보면 이렇습니다:

```
user 7.77s ↔ pro 4.07s | 평균 32.8도 | r_forearm 110도, r_elbow_bend 93도, ...
... 0.27초 간격으로 87개
```

네 가지 문제가 있었습니다.

| 문제 | 처리 |
|---|---|
| 23초 영상에 87개 — 사람이 못 봄 | 연속 프레임을 **구간으로 병합** |
| 한 동작인데 3건으로 보임 | 같은 부위가 0.5초 내 연속이면 한 구간 |
| "96도 차이"만으론 뭘 고칠지 모름 | **부호 있는 오차**를 살려 "더 펴세요/굽히세요" |
| 부위 간 비교가 안 됨 | 부위마다 **가동 범위가 다름** — 전완은 360도 휘두르지만 정강이는 아님. 영상 자체의 부위별 분포로 정규화 |

**구현 중 발견 — 부위별로 묶는 것만으로는 부족했습니다.** 1차 결과에서 상위 5개 중
4개가 같은 시간대(8.3~11.8초)에 몰렸습니다. 재보니 한 시점에 평균 5.4개, 최대 11개
부위가 동시에 걸립니다. 같은 순간의 다리 동작 하나를 정강이·무릎·좌·우로 쪼개서 네
번 말하는 셈이었습니다. → **신체 그룹**(왼팔/오른팔/왼다리/오른다리/상체)으로 다시
묶었습니다.

**점수는 없앴습니다.** 환산 상수가 임의값이라 "45.7점"에 의미가 없었습니다. 대신
**틀린 동작의 개수**를 셉니다.

**신뢰도가 낮은 구간은 지적하지 않습니다.** 프레임 평균 오차가 90도를 넘으면
사용자가 틀린 게 아니라 정렬이 실패했을 수 있습니다(p95가 49도인데 p99에서 119도로
급격히 튀고 최대 178도 — 178도는 물리적으로 정반대 방향입니다). 이런 구간은
"확인 어려움"으로 따로 모읍니다. **틀린 피드백을 주는 것보다 낫다**는 판단입니다.

최종 출력:

```
── 피드백 ── 틀린 동작 47개 (부위별 125개를 묶음)
 1. [ 7.8~11.5s] 오른다리 — 오른쪽 무릎을 더 펴세요   평균 22도, 심각도 3.8
 2. [ 7.8~12.0s] 왼다리  — 왼쪽 무릎을 더 굽히세요
 3. [23.2~25.6s] 왼팔    — 왼쪽 팔꿈치를 더 펴세요
 ...상위 10개
 확인 어려움 2구간 (총 0.3초) — 평가 제외
```

## 4. 트러블슈팅

### 4.1 결과를 믿을 수 없는데 어디가 틀렸는지 알 수 없었다

| | |
|---|---|
| **상황** | 파이프라인은 돌아가고 점수도 나왔지만, 그 점수가 타당한지 확인할 수단이 없었다 |
| **판단** | 정답 없이 고치면 감으로 고치는 것이고, 고쳤는지도 알 수 없다고 봤다. 기능 추가보다 검증 체계가 먼저라고 판단 |
| **원인 분석** | 사람이 정답을 라벨링하려면 시간이 많이 든다. 대신 **정답을 이미 아는 데이터를 합성**하는 쪽으로 방향을 틀었다 — 내가 변형을 가했으니 대응 관계를 안다 |
| **해결** | 시간·공간 변형본 7종 + 재인코딩 대조군 생성. 모든 프레임의 대응 정답을 갖는 dense GT 확보 |
| **결과** | 이후 발견한 버그 3개를 전부 **정량적으로** 확인·수정할 수 있었다 (3.2) |

### 4.2 정렬 오차가 정확히 오프셋 값과 같았다

| | |
|---|---|
| **상황** | 2초 잘린 영상의 정렬 오차 중앙값이 정확히 2.000초 |
| **판단** | 오차가 정확히 오프셋과 일치한다는 건 랜덤한 부정확이 아니라 **아무것도 안 하고 있다**는 신호로 봤다 |
| **원인 분석** | DTW 라이브러리의 1차원 전용 API에 다차원 데이터를 flatten해서 넣고 있었다. `window` 파라미터도 프레임이 아닌 스칼라 단위로 해석되고 있었다 |
| **해결** | 다변량 지원 API(`dtw_ndim`)로 교체 |
| **결과** | 중앙 오차 2.000초 → 0.000초, 대응률 61% → 100%, 속도 60.4초 → 0.07초 |

### 4.3 hybrid 방식이 이론과 반대로 더 나빴다

| | |
|---|---|
| **상황** | 사람을 먼저 검출하고 그 영역만 포즈 추정하는 2단계(hybrid) 방식이, 전체 프레임을 한 번에 처리하는 것보다 결과가 나빴다 |
| **판단** | 2단계가 이론상 더 정밀해야 하는데 반대로 나오니 구현 문제를 의심했다 |
| **원인 분석** | 관절 유효율을 재보니 **같은 포즈 모델을 쓰는데도** MediaPipe 단독 97.2% 대비 hybrid 83.5%였다. 차이는 입력이 전체 프레임이냐 잘라낸 영역이냐뿐 → **crop 단계**를 원인으로 좁혔다 |
| **해결** | hybrid 폐기. 다만 나중에 도입한 ViTPose·RTMPose도 같은 2단계 방식인데 문제가 없었다 — 이들은 라이브러리가 **종횡비를 지키며 패딩·아핀 변환**으로 정규화하는 반면, hybrid는 배열을 직접 잘라(`frame[y1:y2, x1:x2]`) 종횡비가 깨지고 경계에서 신체가 잘렸다 |
| **결과** | **2단계 방식이 문제가 아니라 crop 구현이 문제**였다는 결론. 코드는 지우지 않고 폐기 표시만 남겨 실험 기록으로 보존 |

### 4.4 가설을 세웠다가 측정으로 반증한 사례

| | |
|---|---|
| **상황** | 관절별 오차를 보니 전완·팔꿈치만 유독 컸다 (중앙 30°, 나머지는 5~16°) |
| **판단** | "손목 키포인트가 부정확한데 전완은 짧은 분절이라 작은 픽셀 오차가 큰 각도 오차로 증폭된다"고 추정했다 |
| **원인 분석** | 추정을 확인하려고 대조군에서 feature별 노이즈 바닥을 쟀다. **전완 0.5°, 허벅지 0.6°로 사실상 같았다.** 카메라 기울임에 대한 반응도 (3.0° vs 2.4°) 비슷했다 |
| **해결** | 가설 폐기. 전완 feature 자체는 다른 것들만큼 안정적이므로, 실제 쌍의 30°는 **두 댄서의 실제 팔 동작 차이**이거나 그 구간의 정렬 오류다 |
| **결과** | 둘을 구분하려면 사람이 라벨링한 정답이 필요하다는 것까지 확인. **미해결로 남겨둠** |

### 4.5 실제 촬영 영상이 합성 데이터로는 못 잡는 버그 2개를 드러냈다

| | |
|---|---|
| **상황** | 실제 촬영 영상을 처음 돌리자마자 두 가지가 터졌다 — ① 사람 인식 신뢰도가 이상하게 낮은 영상이 있었고 ② 파이프라인이 아예 크래시났다 |
| **판단** | 지금까지 쓴 합성 변형본은 전부 같은 소스에서 파생돼 조건이 제한적이었다. 실제 데이터가 그 한계를 드러낸 것으로 봤다 |
| **원인 분석 ①** | 세로로 촬영한 영상 중 일부가 신뢰도 중앙값 0.72로 낮게 나왔다. 확인해보니 iPhone은 센서가 항상 가로 프레임을 저장하고 "재생 시 90도 돌려라"는 메타데이터만 별도로 기록하는데, 영상 처리 라이브러리가 이 메타데이터를 적용하지 않고 있었다 — 즉 사람이 옆으로 누운 채로 포즈 모델에 들어가고 있었다 |
| **원인 분석 ②** | 크래시는 시간 정렬 필터가 **절대 시간차**로 기준을 잡고 있어서였다. 실제 촬영에서는 두 영상의 녹화 시작 시점이 몇 초씩 어긋나는 게 정상인데(끝점 완화 기능이 정상 처리하는 상황), 절대 기준 필터가 이 정상적인 고정 오프셋 자체를 전부 "정렬 실패"로 판단해 채점 가능한 구간이 0개가 됐다 |
| **해결** | ① 회전 메타데이터를 읽어 자동 보정하는 로직 추가. ② 필터 기준을 절대 시간차에서 "전체 구간의 중앙값 오프셋 대비 벗어난 정도"로 변경 |
| **결과** | ① 신뢰도 중앙값 0.72 → 0.91. ② 채점 가능 구간 0% → 두 쌍 각각 73%, 31%로 회복(후자가 낮은 이유는 별도 확인 필요 — fps가 서로 다른 쌍이라 더 어려웠을 가능성). 두 버그 모두 오프셋이 2초 이내인 합성 데이터로는 원리적으로 발견 불가능했다 — 실제 촬영이 조건을 넓혀야 하는 이유였다 |

### 4.6 서비스로 옮기면서 드러난 것들

연구 코드를 실제 서비스에 붙이는 과정에서, 연구 단계에서는 보이지 않던 문제들이
나왔습니다. 대부분 **"돌아가는 것처럼 보이는데 틀린"** 종류였습니다.

**같은 입력인데 결과가 매번 달랐습니다**

같은 영상 쌍을 반복 분석했더니 지적 구간 수가 44~52로 흔들렸습니다. 상위 10개
순위도 두 실행에서 하나도 같은 자리에 오지 않았습니다.

새 프로세스에서 해시를 비교해 원인을 좁혔습니다.

| 처리 순서 | 기준 영상 | 연습 영상 |
|---|---|---|
| 기준 → 연습 (3회 반복) | 매번 동일 | **매번 다름** |
| 연습만 (2회) | — | 동일 |
| 기준만 (3회) | 동일 | — |

**영상을 하나만 처리하면 완전히 결정적인데, 해상도가 다른 영상을 앞에서 처리하면
뒤 영상이 비결정적이 됐습니다**(기준 1920×1080 가로, 연습 1080×1920 세로).
차이는 반올림 수준이 아니라 868프레임 전부가 달라지고 최대 121.9픽셀이었습니다.

→ **영상마다 별도 프로세스에서 추출**하도록 바꿔 해결했습니다. 3회 반복에서
구간 수·평균 오차·상위 10개 순위가 완전히 일치합니다.
부수 효과로 오히려 빨라졌습니다(110초 → 71초).

> **왜** 해상도가 바뀌면 비결정적이 되는지는 확인하지 못했습니다.
> MediaPipe/TFLite 내부 동작이라 격리로 우회했습니다.

**사람이 보는 결과물이 정렬을 쓰지 않고 있었습니다**

비교 이미지와 비교 영상을 만드는 코드가 **기준 영상 N번 프레임과 연습 영상 N번
프레임을 짝지어** 보여주고 있었습니다. 정렬을 하는 이유 자체가 같은 동작이 서로
다른 시각에 있기 때문인데, 정작 사람이 눈으로 보는 결과물에서 그 정렬이 버려지고
있었습니다. 테스트 영상은 시작 시점이 3.7초 어긋나 있어 두 사람이 완전히 다른
동작을 하고 있었습니다.

**보안: 인증이 사실상 없었습니다**

`X-User-Id` 헤더 하나로 사용자를 판별하고 있어서, 헤더 숫자만 바꾸면 남의 연습
기록과 영상을 볼 수 있었습니다. 영상 재생 API는 `?userId=123` 쿼리로도 인증을
받았는데(`<video src>`가 헤더를 못 붙인다는 제약 때문), URL의 숫자만 바꾸면
남의 영상이 재생됐습니다.

→ JWT를 **httpOnly 쿠키**로 옮겼습니다. 브라우저가 `<video src>` 요청에도 쿠키를
자동으로 실어 보내므로 쿼리 파라미터 우회로 자체가 불필요해졌습니다.

**"운영에서는 비활성"이라고 적어두고 확인하지 않았습니다**

개발용 아이디/비밀번호 로그인을 운영에서 끄려고 컨트롤러 **메서드**에
`@Profile("dev")`를 붙였습니다. 테스트를 써 보니 아무 효과가 없었습니다 —
`@Profile`은 빈(클래스) 단위로만 동작합니다.

| 엔드포인트 | 의도 | 실제 |
|---|---|---|
| `POST /api/auth/signup` | 404 | **200 — 계정이 만들어짐** |

운영에 비밀번호 계정 생성 경로가 그대로 열려 있었습니다. 클래스를 분리하고
테스트로 404를 고정했습니다.

> 이 건에서 배운 것: **"운영에서는 꺼진다"는 말이 아니라 테스트로 확인해야 합니다.**

**배포 환경이 정해지자 포즈 모델을 바꿔야 했습니다**

분석 서버를 맥미니(Fedora Asahi Remix, **aarch64**)로 정하고 나서 확인해보니
**MediaPipe 0.10.x에는 linux aarch64 휠이 없었습니다** — 설치 자체가 불가능합니다.

그런데 이걸 계기로 더 중요한 문제가 드러났습니다. 정렬 정확도를 측정할 때 쓴
백엔드는 **YOLO**인데 서비스는 **MediaPipe**로 돌고 있었습니다. 즉
**문서에 적힌 검증 수치가 서비스의 수치라고 말할 수 없는 상태**였습니다.
품질도 MediaPipe Full이 5개 중 꼴찌였는데([3.4](#34-모델-선정--예측이-빗나간-기록)),
"교체 비용이 크다"는 이유만으로 유지하고 있었습니다.

YOLO로 통일한 결과:

| | MediaPipe Full | **YOLO (yolov8n)** |
|---|---|---|
| 평균 오차 | 28.0도 | **24.9도** |
| 채점률 | 81.7% | **83.6%** |
| 소요 | 약 50초 | **35~38초** |

연구에서 잰 값(24.41도)과 24.9도로 근접해 이식이 정상임도 함께 확인됐습니다.
**측정한 것과 서비스하는 것이 같아졌습니다.**

**분석 중에 서버가 죽은 것처럼 보였습니다**

`/analyze`가 `async def`인데 본문은 전부 블로킹(다운로드·OpenCV·MediaPipe)이었습니다.
`await`가 하나도 없어 이벤트 루프를 1분 넘게 독점했고, 그동안 헬스체크조차 응답하지
못했습니다.

| 분석 중 헬스체크 | `async def` | `def` |
|---|---|---|
| 응답 | **타임아웃(5초)** | 200, 0.9~2.8ms |

평범한 `def`로 바꾸면 FastAPI가 스레드풀에서 실행해 루프가 계속 돕니다.
동시 실행 제한(429)도 이걸 고친 뒤에야 의미가 있었습니다 — 루프가 막혀 있으면
429조차 응답할 수 없기 때문입니다.

## 5. 한계 (미해결)

정직하게 남깁니다.

- **잘 추는 사람에게 정확하고, 못 추는 사람에게 부정확합니다.** 3.6에서 확인한
  구조적 한계입니다. 사용자가 동작을 틀릴수록 정렬이 어긋나고, 정렬이 어긋나면
  채점도 틀립니다. 정작 못 추는 사람이 이 서비스의 주 사용자라는 점에서 가장
  뼈아픈 한계입니다. 완화책(신뢰도 낮은 구간을 지적하지 않음)은 넣었지만 해결은
  아닙니다.
- **정렬 오류를 자동으로 감지할 수 없습니다.** "이 정렬은 틀렸다"를 알려줄 신호를
  5개 시도했지만 모두 예측력이 없었습니다(상관계수 0.03~0.26). 이유가 원리적입니다 —
  실패 양상이 "불확실한 매칭"이 아니라 **"확신에 찬 틀린 매칭"** 이라, 틀린 지점이
  오히려 더 좋아 보입니다.
- **피드백 내용의 타당성이 검증되지 않았습니다.** "왼쪽 무릎을 더 굽히세요"가 실제로
  맞는 지적인지는 사람이 영상을 보고 판단해야 합니다. 현재는 파이프라인이 의도대로
  동작한다는 것까지만 확인됐습니다.
- **분석 서버 실측이 아직 개발 기기 기준입니다.** 위 수치는 MacBook Air(M2)에서
  잰 것이고, 실제 분석은 맥미니(Fedora Asahi Remix)에서 돌립니다. 사양이 달라
  소요 시간은 달라질 수 있습니다.
- **포즈 추정 정확도(mAP/PCK)의 순위는 확정하지 못했습니다.** 3.4의 지표는 정확도의
  대리 지표지 정확도 자체가 아닙니다. 뼈 길이가 안정적이어도 일관되게 틀린 위치를
  찍을 수 있습니다.
- **겹침 스트레스 테스트 데이터가 없습니다.** 보유한 영상 8개 모두 검출 실패
  0프레임이라, 정작 중요한 겹침 구간에서의 성능은 미검증입니다. **브레이킹처럼 몸이
  겹치는 빠른 동작의 관절 오인식**은 여전히 열린 문제입니다.
- **임계값들이 잠정값입니다.** 신뢰 불가 판정(90도), 구간 병합 간격(0.5초) 등은
  영상 1~2개의 분포에서 정했습니다. 데이터가 쌓이면 재조정이 필요합니다.
- **배포가 아직 완료되지 않았습니다.** 인증·저장소·분석 파이프라인은 로컬에서 전
  구간 검증했지만, 실제 서버(EC2 + 맥미니)에 올려 도메인으로 접속하는 단계는 진행
  중입니다. 이 README의 성능·동작 수치는 전부 **로컬 실측값**입니다.
- **피드백 문구의 타당성과 별개로, 겹침 구간의 추출 품질이 미검증입니다.**
  위 항목과 같은 이유로 브레이킹 같은 동작에서는 어떻게 나올지 모릅니다.

## 6. 회고

**배운 것**

- **정답을 만드는 게 먼저였습니다.** 처음엔 기능부터 늘렸는데, 결국 "이게 맞나"를 확인할
  수 없어 멈췄습니다. 정답을 합성하는 방법을 찾고 나서야 버그 3개를 정량적으로 잡을 수
  있었습니다. 검증 체계가 기능보다 앞선다는 걸 몸으로 배웠습니다.
- **측정이 제 예측을 여러 번 뒤집었습니다.** "SOTA 모델이 이길 것", "손목 노이즈가
  원인일 것" — 둘 다 틀렸습니다. 틀린 예측을 지우지 않고 기록으로 남겼습니다.
- **문제를 잘 나누면 해법이 따라옵니다.** "촬영 조건"을 별도 축으로 분리하고 나서야
  좌표 대신 각도를 쓴다는 답이 나왔습니다.
- **"돌아간다"와 "맞다"는 다릅니다.** 서비스로 옮기면서 나온 문제들([4.6](#46-서비스로-옮기면서-드러난-것들))은
  전부 에러 없이 200을 반환하던 것들이었습니다. 비교 이미지는 정렬을 무시한 채
  멀쩡히 생성됐고, 인증은 헤더만 바꾸면 뚫렸으며, 같은 입력이 매번 다른 답을 냈습니다.
  로그만 봐서는 전부 정상이었습니다.
- **문서에 적은 것이 사실인지 확인해야 합니다.** "운영에서는 개발용 로그인이
  비활성"이라고 적어두고 검증하지 않았는데, 테스트를 써 보니 그대로 열려 있었습니다.

<summary><b>로컬 실행 방법</b></summary>

### 요구 사항

- **Python 3.10 고정** — 3.11 이상에서는 MediaPipe의 `mp.solutions` API가 사라져 동작하지 않습니다
- Java 17 (Spring Boot)
- Node.js (React 19 + Vite)

### 연구·검증 모듈 (`model-research`)

```bash
cd model-research
python3.10 -m venv venv          # 시스템 기본 python이 3.13이면 그냥 python으로는 안 됨
source venv/bin/activate
pip install -r requirements.txt

# 분석 실행 — 반드시 프로젝트 루트에서 -m 으로 (경로 직접 실행 시 import 깨짐)
python -m src.main --pose-backend yolo --feature angle

# 검증 데이터 생성 및 측정
python -m tools.make_variants --video data/videos/real/user_dancer.mp4
python -m tools.eval_alignment --mode variant --gt data/variants/user_dancer__local0.50.gt.json
python -m tools.eval_pose_quality --video data/videos/real/user_dancer.mp4 \
    --models yolo:models/yolov8n-pose.pt yolo:models/yolo11x-pose.pt
```

모델 가중치(`models/*.pt`)는 최초 실행 시 자동 다운로드됩니다.

### AI 서버 (`ai-server`)

```bash
cd ai-server
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

# 127.0.0.1에만 바인딩합니다. 이 서버에는 인증이 없고,
# 접근 통제를 "네트워크에서 닿을 수 없다"에 의존합니다.
uvicorn main:app --host 127.0.0.1 --port 8000
```

### API 서버 · 프론트엔드

```bash
cd web-service/api-server && ./gradlew bootRun    # dev 프로파일이 기본
cd web-service/frontend  && npm install && npm run dev
```

개발 환경에서는 **R2 자격증명 없이도** 전 과정이 돌아갑니다
(`storage.type=local`, 로컬 디스크가 presigned URL을 흉내냅니다).
소셜 로그인 대신 테스트 계정으로 들어갈 수 있습니다 — `test` / `test1234`
(이 계정과 로그인 경로는 `dev` 프로파일에만 존재합니다).
